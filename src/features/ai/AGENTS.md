# src/features/ai/ — AI Study Assistant & Content Generation

## Purpose

AI Study Assistant and Content Generation bounded context. Provides conversational grounded context, document summaries, active selection explanations, and LLM-assisted question and flashcard synthesis.

## Ownership

- `components/` — Chat assistant UI presentation: `AiChatDrawer` (thin container), `AiChatDrawerHeader` (its subtitle is deliberately **grounding-neutral** — the mode is per-conversation and mutable, so a header claim about it would contradict the control; the per-turn badge is what states what a turn carried), `AiDrawerToggleButton`, `AiChatMessage` (renders the per-turn **"Material attached"** tag on grounded assistant turns only, from `metadata.grounding`), `AiChatMessageList`, `AiChatInput`, `AiChatHistoryPanel`, `AiChatErrorBanner`, `AiStreamingIndicator`, `AiMessageUsage` (per-turn `model · tokens · cost` footer), `AiSessionMetrics` (conversation totals + context-window readout, from an estimate the drawer computes), `AiGroundingControl` (thread-scoped grounding toggle `'whole' | 'none'`, each mode carrying a one-line description resolved from the current value via `utils/aiGroundingNotice.ts`, mirroring the model picker's tagline notice), `AiModelPicker` (model choice for the next request, with the over-budget / cooldown / switched-off notice; `layout="inline"` is the drawer composer's horizontal strip, `layout="stacked"` is the Settings card's full-width row with the notice below and no surface of its own; `controlLabel` renames the control for a surface whose next request is not a chat message), `AiSelectionThreadModeControl` (dumb segmented choice for where selection actions reply — value and persistence live in `useAiSelectionThreadMode`; same `inline` / `stacked` layout contract as the picker), `AiSettingsSection` (the Settings screen's AI section: preferred model + material-inclusion default + selection thread mode, composed from the same units and cache entries the drawer uses), `AiChatDrawerComposer` (the bottom strip — metrics + grounding + picker + composer as one unit, so the guard the picker explains and the input enforces are derived in one place).
- `hooks/` — `useAiChatThread` (session lifecycle, turn loading, streaming, wait/stall state, grounding state and mutation, prompt retry retention, and the persisted rate-limit cooldown), `useAiModelSelection` (the per-request model choice, remembered per device and resolved through the catalog, with `refreshCatalog` for a server refusal), `useAiSessionDeletion` (confirm-then-delete for a session or the whole scope), `useAiSelectionAction` (reader selection → one chat turn, deduplicated; dispatches only once the session has settled (`ready`) and clears the selection only once the turn is on the transcript, so a mount-time abort cannot orphan an empty session with the request already forgotten), `useAiAutoScroll` (transcript viewport pinning), and the unwired `useAiStreamChat` (kept for the streaming port contract; the drawer uses `useAiChatThread`).
- `hooks/queries/` — `useAiModelCatalog` (the **shared** catalog cache state: one `['ai','model-catalog']` entry for every consumer, plus `refreshCatalog`), `useAiGroundingContext` (querying next-request serialized document length from `GetAiGroundingContextUseCase`), `useAiSelectionThreadMode` (querying and mutating the reader-selection thread-mode preference), and `useAiGroundingDefault` (querying and mutating new-conversation grounding preference).
- `queries/` — `aiQueryKeys` (the AI cache namespace: `modelCatalog`, `groundingContext`, `groundingDefault`, `selectionThreadMode`).
- `utils/` — AI markdown sanitization schema (`aiMarkdown.ts`), wait-label escalation ladder (`aiActivity.ts`), session naming (`deriveSessionTitle.ts`), session timestamps (`formatSessionTime.ts`), token/cost formatting (`formatAiUsage.ts` — `formatTokenCount`/`formatUsdCost` are shared by per-turn and per-session labels, and the per-turn summary resolves the *serving model's display name*), conversation totals + context estimation (`aiSessionMetrics.ts`), rate-limit cooldown policy **and persistence** (`aiRateLimit.ts` — `resolveCooldownSeconds`/`formatCooldownNotice`/`secondsUntilDeadline`/`readCooldownDeadline`/`writeCooldownDeadline`, plus `mergeCooldownDeadline` for the monotonic rule), model-picker notice copy (`aiModelPickerNotice.ts` — `resolvePickerUnavailableNotice`/`resolvePickerNotice`, pure so each state's wording is testable without rendering), selection action prompts (`selectionActionPrompt.ts`), and deletion dialog copy (`deletionDialogCopy.ts`).
- `generator/` — AI Content Generator sub-capability:
  - `components/`: `AiQuestionGeneratorDialog`, `AiFlashcardGeneratorDialog` (neither takes a `documentMarkdown` prop — the source document is resolved from `materialId` in the use case; each renders a `SynthesisModelControl` and disables its buttons with a stated reason when the assistant is unavailable), `SynthesisModelControl` (the shared model control step: the same `AiModelPicker` the chat drawer and Settings use, given `layout="stacked"` and its own accessible name, plus a one-line statement that the choice applies to **this batch only** — `isOverBudget` / `cooldownSeconds` stay at `false` / `0` because both are facts about a *conversation*, and a generation is a single request with no history; a switched-off assistant replaces the control with the reason), `GeneratedBatchHeader` (the shared review header: generated/selected counts plus the dropped-item warning, so the two review steps cannot drift), `DraftTagList` (the shared tag row on both preview cards — tags are set on a draft *before* it is persisted, so review is the only chance to see what an item will be filed under; it is read-only, and a draft with no proposed tags says "No tags suggested" rather than leaving a gap that reads as a rendering bug), `GeneratedQuestionPreviewCard`, `GeneratedFlashcardPreviewCard`.
  - `hooks/`: `useAiQuestionGenerator`, `useAiFlashcardGenerator` (each resolves the device's preferred model through the shared catalog and injects it into the request, and exposes `modelName` + `isAiUnavailable`).

## Local Contracts

- `AiChatDrawer` is hosted at the workspace level in `MaterialWorkspace`. It is a non-modal overlay with its own backdrop, so it locks page scroll itself through the shared `useBodyScrollLock` (`isOpen`) — the same page-behind-will-not-scroll behaviour the native-`<dialog>` surfaces get from `useModalDialog`.
- **Conversations are sessions, and a session is the unit of history.** Sessions are scoped to one study material (`AiThread.materialId`); a material holds many, ordered newest-first by `updatedAt`. `ResolveAiThreadUseCase` reopens the newest and **never creates one**, so an unused material shows the composer's empty state instead of an empty history row. `CreateAiThreadUseCase` always inserts a distinct session, so **New chat never deletes or replaces earlier conversations**.
- **Grounding belongs to the conversation, not per-send caller props.** `AiThread.grounding` (`'none' | 'whole'`) controls whether material document text is attached. `documentContext` was removed from `AiChatDrawerProps` and `MaterialWorkspaceScreen`: `AiGroundingResolver` attaches the document from thread state on send, and `GetAiGroundingContextUseCase` via `useAiGroundingContext` provides the pre-capped serialized character count for the context meter. The composer exposes `AiGroundingControl` with a toggle (`Whole material` vs `No material`) for the active thread only; the new-chat default lives in Settings (`AiSettingsSection`), so a per-thread choice cannot silently become a global one. Because the thread's mode is mutable, each settled turn also snapshots the mode it was sent under onto `AiMessageRecord.metadata.grounding`, so a `none → whole → none` thread keeps a legible mixed transcript; `AiChatMessage` surfaces it as a quiet **"Material attached"** tag — the request fact only, never "answered from material", since what the model did with the material is unverifiable.
- **History projection and prompt retention.** `projectRequestMessages` is the single shared projection for request payloads and context metering: assistant error turns with text are kept for continuity, while empty error turns and their preceding user prompt are dropped together. `useAiChatThread` retains the last attempted prompt in hook state, ensuring `retryLastPrompt` functions even if turn pair persistence failed.
- **There is no user-facing tutor-mode selector.** `AiTutorMode` survives as a server-side prompt capability only; the client always sends `assistant`. Quiz/flashcard generation and the reader's Explain/Simplify/Example actions are prompt presets on their own surfaces and have never depended on modes or thread identity.
- **A session is named from its first prompt** (`deriveSessionTitle`, fire-and-forget via `RenameAiThreadUseCase`) so history rows are identifiable. Failures must never break the conversation.
- **In-flight assistant work is always visible in the transcript, not only in the composer.** `AiChatMessageList` projects a provisional assistant turn from `streamingText`; before the first token it shows the `activity` label (`resolveAiActivity`): rotating generic labels, escalating to an explicit elapsed-seconds stall warning at `AI_ACTIVITY_STALL_MS`, and abandoning the request at `firstTokenTimeoutMs` (default `AI_FIRST_TOKEN_TIMEOUT_MS`) with a retryable `TIMEOUT` error.
- **Request-level failures render in `AiChatErrorBanner`** (stalled first token, transport failure, session creation failure). Failures that were persisted as their own turn carry the error inline instead, and the hook clears the banner only then — a failure that persisted nothing keeps its retryable banner rather than dissolving into an empty transcript with no explanation.
- **A settled assistant turn reports what it actually cost.** The Worker forwards the provider's token usage and the serving model on the terminal `done` event; `SendChatMessageUseCase` persists both on the turn, and `AiMessageUsage` → `formatAiUsage` → domain `estimateAiCostUsd` renders the count and the derived charge. The prompt/completion split lives in the element's `title`, not in the transcript. An unpriced model shows tokens with no cost — unknown is never rendered as free, and telemetry is never fabricated client-side.
- **The drawer reports what a conversation has cost and how full the model's window is** (`AiSessionMetrics`, above the composer; it steps aside while the history panel shows). Two kinds of number, deliberately not blended:
  - **Measured** — session totals summed from the provider's own reports on settled turns (`summarizeSessionUsage`). The same footer names **which model served that turn** (`formatAiUsage` → `modelLabel`), resolved through the catalog by catalog id *or* the provider id older builds stored, because a conversation may mix models and two answers from different models must not look identical. An id the catalog cannot name renders as itself — never mislabelled as another model. A total cost is withheld entirely when any turn was unpriced, because a partial sum is a lower bound and publishing it as the conversation's cost would misstate it.
  - **Estimated** — the share of the selected model's window the *next* request will occupy (`estimateSessionContext` → domain `estimateContextUsage`). Derived from character counts at `AI_CHARS_PER_TOKEN`, with the document and selection capped through `AiContextBuilder` so the estimate cannot drift from what is actually sent. The last measured `promptTokens` rides the tooltip as calibration.
  - **The estimate is computed once**, in `AiChatDrawer`, and passed to `AiSessionMetrics` as `context` (`SessionContextEstimate`): the meter and the over-budget send guard then read the same number from one calculation, and there is a single place to edit when the estimator changes. The strip decides whether it has anything to show from the estimate's own capped character counts, so it re-derives nothing.
  - **The window, output reservation, and document cap are per-model catalog facts**, not constants: `estimateSessionContext({ modelId })` resolves them from `domain/ai/services/aiModelCatalog.ts` (defaulting to the catalog default), so a request on a large-window model is not metered — or document-capped — as if it were the default model. For the default model the served document cap is ~4k tokens against a ~19.9k prompt budget, so **conversation history, not the document, is what approaches the ceiling**; that is not true of a 256k-window model, whose larger cap lets the material itself be large.
- **Model choice is per request, not per session.** `AiChatRequest.model` (and `SendChatMessageInput.model`) carries an app-facing catalog id; the Worker resolves it and reports the serving model on the turn, so a conversation may mix models and every turn stays individually priced. Conversations are **not** pinned to a model and `AiThread` stores none. `useAiModelSelection` owns the choice — catalog-first, device-local via the `PreferencesRepository` (`getPreferredModelId`, shared `preferred-model` cache entry), and always resolved through the catalog, so a retired or unknown preference degrades to the catalog default instead of being sent and refused. A `MODEL_UNAVAILABLE` refusal from the Worker re-reads the catalog (`refreshCatalog`, wired in `AiChatDrawer`) instead of retrying the refused model — the server can disable a model out of band (`AI_DISABLED_MODELS`), and a stale client catalog is the one thing that could still offer it. **The catalog itself is shared cache state, not hook state** (`hooks/queries/useAiModelCatalog`): every consumer reads one `['ai','model-catalog']` entry, so two surfaces cannot disagree about which models exist, and `refreshCatalog` invalidates that key rather than asking each caller to re-run its own effect. The bundled mirror is the query's `initialData` — deliberately marked already-stale (`initialDataUpdatedAt: 0`) so the first mount still fetches — which is what keeps the picker working with no network. `AiModelPicker` renders **only when the catalog offers more than one model** (a single-option control would imply a capability that is not there) — except when nothing is selected (`defaultModelId: null`), where it stays visible to ask for a choice rather than picking one silently — and it hides itself if the fetch never lands — the bundled mirror always answers. **Generators choose per batch, not through the preference.** `useAiQuestionGenerator` / `useAiFlashcardGenerator` resolve their effective model the same way (`resolveAiModelSelection` against the shared catalog, so an override the server retired degrades to the default rather than being sent and refused), but the dialog picker writes a hook-local override that is **never persisted** — selecting MAX for one batch must not re-route later chat messages onto a shared, rate-limited endpoint. The override is deliberately **not** cleared by `reset()`: it sits with the dialog's other generation settings (count, difficulty, focus), and clearing it on Back or Retry would silently substitute a model the user did not choose. Settings states the split: the preferred model is what chat uses and what each generator batch starts from.
- **Three reasons to hold a send, and each says which problem it is.** They live in `AiChatDrawerComposer` beside the controls that explain them, derived from the same estimate the metric strip shows, against the *selected* model:
  - **Over budget** — the next request would exceed the selected model's prompt budget, so sending is blocked (`AiChatInput.isSendBlocked`, typing still allowed) and the notice says to start a new chat or switch model. Only an overshoot blocks: the request has not been refused until it is sent.
  - **Rate-limit cooldown, persisted and monotonic** — MAX is free but shared (~5 prompts/minute **per IP**, and a deployment shares one Worker egress IP), so a refusal is normal traffic. The deadline is written to `STORAGE_KEYS.ai.rateLimitUntil` as **absolute epoch ms** and rehydrated on mount, because the wait describes the provider's window rather than this tab: without it, a reload spends the very next request on another refusal. A stored deadline further out than the policy maximum is discarded rather than honored (only a stale or hand-edited value could be hours away). A refusal may only ever **push the deadline out** (`mergeCooldownDeadline`): the cooldown starts after an `await`, so a slower older turn can report its rate limit after a fresher one already did, and a stale "try again in 3s" must not cancel the "try again in 45s" the newer one established. The wait the provider named (`retryAfterSeconds`) starts a cooldown in `useAiChatThread`; the composer blocks sends until it elapses, and the guard covers retries too, not just the composer. The countdown is computed from an absolute deadline, so a backgrounded tab resumes at the right remaining time rather than drifting.
  - **Nothing legitimate to send on** — `selectedModel === null`, which is either the assistant switched off by the deployment or a catalog with no default to inherit (see below). Not a user-fixable state, so the picker replaces its control with the reason rather than offering a choice.
- **The assistant can be switched off by the deployment, and the client says so rather than looking broken.** The served catalog carries `availability` (`available` | `disabled`, from the Worker's `AI_CHAT_DISABLED` switch) and `defaultModelId: null` when the default is not servable. `isAiCatalogDisabled`/`resolveAiModelSelection` (domain) turn that into `isAiDisabled` and a `null` selection; the drawer blocks sending, `AiModelPicker` shows "temporarily unavailable" instead of a control, and **nothing is substituted** — the same no-silent-fallback rule as the server. `WorkerAiModelCatalogRepository` never persists a disabled catalog, so an outage cannot survive in the cache after it is over. A `MODEL_UNAVAILABLE` refusal still re-reads the catalog (`refreshCatalog`), which is also how a client finds out the assistant went away mid-session.
- `AiChatDrawer` stays a thin container. Session lifecycle and streaming live in `useAiChatThread`, the deletion flow in `useAiSessionDeletion`, the selection handoff in `useAiSelectionAction`, the bottom strip (totals, model choice, send guard) in `AiChatDrawerComposer`, and presentation in the components above. Put new logic in one of those rather than back in the drawer — the drawer is where feature branches accumulate fastest, and at the current size an added conditional is enough to trip `react-doctor/no-high-complexity-react-function`.
- **The server's own reach is bounded and cancellable.** Two deadlines run per pull (`AI_FIRST_EVENT_TIMEOUT_MS` 25s to the first event, then `AI_STREAM_IDLE_TIMEOUT_MS` 45s of silence); the first-event one is deliberately tighter than the client's `AI_FIRST_TOKEN_TIMEOUT_MS` (30s) so the Worker's coded, model-attributed `TIMEOUT` is what the user sees instead of the client's generic "did not start responding". **The ordering is pinned on both sides rather than imported across the boundary**: the Worker's catalog coherence test asserts its own deadline is under 30s, and `aiActivity.test.ts` pins this constant to 30s — so changing either number means changing a pinned value in two places, and neither side's tests reach into the other's layer. A deadline, a Stop, or a closed consumer **cancels** the provider request and skips every later write, so a `TIMEOUT` turn is terminal rather than a drawer that never settles, and a client cancellation arrives as `ABORTED` (499) rather than a misleading 502.
- Section context extraction bounds prompt tokens to current headings and selections via `src/domain/ai/context/extractSectionContext`.
- Conversation state persists locally in IndexedDB (`aiThreads`, `aiMessages`). AI history is **not** part of the sync entity model, so sessions are device-local.
- Content generators emit typed question/flashcard drafts validated by domain schemas (`validateQuestionDraft`). They run under the **same model contract as chat**: the resolved app-facing model is forwarded to `generateStructured`, the model's own `maxOutputTokens` is the output budget and its `maxDocumentContextChars` caps the document, and the source document comes from the shared `AiGroundingResolver` — never from a caller-supplied string. Nothing is sent when the assistant is off or no model resolves.
- **Selection actions reply where the preference says.** `AiSelectionThreadMode` (`'latest' | 'new'`, default `'latest'`) decides whether Explain/Simplify/Example continue the material's newest conversation or open a distinct one. `'latest'` sends on the resolved session; `'new'` rides `sendMessage`'s send-time `freshSession` override, which bypasses the active thread *and* its history so the previous conversation stays untouched. The drawer reads the mode through the shared `useAiSelectionThreadMode` query — the same entry the Settings surface writes — and its dispatch still waits for the session to settle first.
