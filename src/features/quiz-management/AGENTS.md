# src/features/quiz-management/ — Quiz & Question Management

## Purpose

Authoring feature for creating, editing, publishing, and archiving questions and quizzes. Separate from the learner quiz-taking experience (`src/features/quiz/`). Provides a Question Bank manager, Quiz Catalog, the quiz canvas builder (Google Forms-style authoring, rendered on a dedicated `quiz-canvas` app-shell route so the global sidebar stays visible), type-specific question editors, and publishing workflows. The quiz canvas builder is a sub-feature — see `canvas/AGENTS.md` for its contracts.

## Local Contracts

- No cross-feature imports — this feature does not import from `src/features/quiz/`
- **The two choice editors are two wrappers over one row — never a `selection` variant prop.** The divergence is data shape (`correctIndex: number` vs `correctIndices: number[]`), so each wrapper keeps its own selection and index logic while `ChoiceListRow` takes `shape` + `isSelected` and callbacks only. A presentation-only divergence may justify a variant prop; a data-shape divergence does not.
- Query repository access via application context; mutations call `context.useCases.quizManagement`
- **The launch intent's lifecycle is LATCH → RETIRE, in that order, and `close()` is the idempotent fallback.** The claim is taken during render (the guarded `useVisitedTabs` pattern) so the dialog is configured on the **first paint** — preselected types and all — and the claimed intent is **latched into the hook's own state**, which is what `initialTypes` and the return label are read from. Retirement is then asked for by an effect **keyed on the latch**, and it fires *after* the commit.
  - **The effect must be keyed on the latch, not on an "unclaimed" flag.** A render-phase claim calls `setState` during render, so React re-renders the hook before committing and any "still unclaimed" flag is already `false` by the time an effect registers. Keyed on the flag the effect is unreachable — the shape the code had before Sep 2026, with `close()` silently carrying the entire one-shot guarantee. Keyed on the latch it runs on the render that commits.
  - **The latch is load-bearing, not bookkeeping.** Retiring during the claim, or by clearing the latch, empties the channel and closes the dialog on the same commit. The latch is what lets the effect run *after* the dialog is open and configured. Retirement is *asked for* rather than written into the owner mid-render, because emptying the owner's state during render is a cross-component render-phase update, which React rejects.
  - **Retirement is at-most-once per claim and is identity-checked twice.** The effect fires only when the channel's pending intent **is** the latched claim (so a launch that arrived while another was latched is left alone to be claimed when the current dialog closes), and a ref guard makes the call once per claim even if a consumer re-creates `onRetire` every render.
  - **`close()` retires the LATCHED claim, never the channel's current one** — that is what makes it safe under supersession — and drops the latch. It is idempotent: a claim the effect already retired is a no-op, and a dialog the Bank opened itself retires nothing. Closing therefore works whether or not the effect has run.
  - **A superseded dialog cannot clear the launch that replaced it.** Because both retirement sites name their target, an old dialog's `close()` reaches the owner with a target the owner no longer holds and is ignored. `onRetire` takes the intent as an argument precisely so the owner can make that comparison; an implementation empties its state unconditionally and the guarantee is gone.
- **An armed launch expires with the material it was armed for.** `ShellRoutes` renders the workspace screen **without a `key`**, so the instance (and its `useState`) is reused when the route's material changes. The screen therefore drops a pending intent whose `materialId` no longer matches the route — a render-phase adjustment, like `useVisitedTabs` and `lastInMode`. Without it, arming for A, opening B, and returning to A re-fires a request the user made long ago. An intent for another material is *not* consumed by the Bank that declines it; the owner is what expires it.
- **Quiz Draft Repository Exception (CQRS):** `useQuizCanvasEditor` directly calls `context.repositories.quizDraft.saveDraft()` and `.deleteDraft()` for crash-recovery draft autosaving. This is an intentional architectural exception — quiz drafts are ephemeral editor state, not business entities. Creating `SaveQuizDraftUseCase` / `DeleteQuizDraftUseCase` wrappers would add no meaningful domain behavior. The primary save path (`handleSave`) correctly routes through `SaveQuizUseCase`.
- Query keys match the assessment namespace: `['assessment', 'questions', materialId]` and `['assessment', 'quizzes', materialId]`
- `QuestionStatus` lifecycle: `draft` → `published` → `archived`
- `QuizStatus` lifecycle: `draft` → `published` → `archived`
- Archiving is soft-delete — never hard-deletes questions that may be referenced by quizzes
- `QuizQuestion` version pinning: quizzes snapshot `questionVersion` at creation time
- UI components contain zero grading, scoring, or persistence logic

- **The Bank is a validating authoring surface, and it is the one that was missing until Sep 2026.** `CreateQuestionUseCase` / `UpdateQuestionUseCase` call `domain/quiz/validation/questionPayloadValidation` — the single owner of the rule — and return `{ success: true, question } | { success: false, errors: string[] }`, the same shape `SaveQuizUseCase` uses. This is a call to the existing owner, **not a third copy** of the rules. It matters here more than anywhere else in the feature: the type-specific editors emit **malformed default payloads for four of the five types** (`identification` `{correctAnswer: ''}`, `fill_in_blank` `{template: '', blanks: []}`, `multiple_select` `{correctIndices: []}`, `multiple_choice` `{choices: ['','']}`), so before the gate a malformed row was reachable by typing a prompt and nothing else. The editor holds the content that repairs such a row, so the refusal is rendered **in the dialog**, never thrown away as a toast. **A new authoring surface must call the owner or deliberately not be one.**
- **`onCreate` / `onUpdate` return the mutation promise, not `void`.** The dialog needs the verdict to decide whether to close, so `QuizManagementTab` wires `mutateAsync` and `QuestionBankTab.handleSave` passes the promise straight through. A `void`-returning handler would silently restore the old behaviour of closing on a success toast over a row that was never written.
- **The Bank's tag filter and its search field are independent controls.** A chip toggles membership in `selectedTags` and never writes into the search box; the search box narrows the list by prompt/tag text and never touches `selectedTags`. The empty-state "Clear filters" affordance clears both. Matching is **OR within the tag facet** and **AND across search/type/difficulty/status**, and a question is shown if it carries *any* selected tag — the same model as the Material Library. Chip rendering across both surfaces is owned by the filter bar's sub-rules below; the card chips' own rule set is owned by `components/questionBank.stylex.ts`.
- **The Bank's filter bar: one implementation, two surfaces, three rows.** Sub-rules for `QuestionBankFilterBar`; its ownership stays in the table row above.
  - **The tag facet is ported from the Material Library's `LibraryFilterBar`, not imported from it.** Capped at `VISIBLE_TAG_COUNT` (8) frequency-ranked tags, with a **selected tag never hidden by the cap** (`i < VISIBLE_TAG_COUNT || selectedTagSet.has(tag)`); the remainder sits behind a `+N more` expander with a `Show fewer` collapse. The expander control stays a **text affordance**, never a pill.
  - **One `selectedTags` array, two surfaces.** A section chip and a card chip for the same tag are the same control. A selected filter-bar chip additionally renders a decorative `aria-hidden` `X` confirming that clicking again removes the filter — it is **not** a second hit target, and the pill's accessible name stays the tag (no nested control).
  - **Three rows, in this order.** (1) Search + structured selectors on ONE full-width row (`searchRow`); `selectorGroup` carries **no right border** — the divider ported from the Library's `membershipGroup` bordered a lens that had controls to its right, and here nothing followed it, so it dangled at the row's end separating nothing; the row's own `gap` does the spacing. The `Filter` trigger on <769px lives inside `selectorGroup`. (2) The tag facet on its own **full-width** row at **≥769px** — a variable-length chip set with an expander cannot share a line with fixed-width dropdowns without reflowing as tags are selected. **Below 769px the row is not rendered at all**: the same chips render *inside* the existing `Filter (N)` disclosure (`mobileFilterPanel`), so the content begins directly under row 1. (3) The entry-point actions **last**, right-aligned by `marginLeft: 'auto'`, which as a cross-axis auto margin in the column `filterContainer` pushes the row right instead of letting `align-items: stretch` leave the buttons on the left. Each group keeps its own `role="group"` / `aria-label` landmark; all three share one parent — the bar.
  - **The bar adds no clear/count control** — the Bank's clear-filters affordance is the empty state's. Its stylesheet declares **no `borderRight*` on any rule**, pinned by the `filter bar rule sheet` block in `components/__tests__/QuestionBankTab.test.tsx`.
  - **The 8-tag cap and its expander are ≥769px-only**; inside the panel every tag is shown, because a cap there would nest a second disclosure inside the first — the cost the move exists to remove.
  - **The chips are one implementation in two places, not two implementations.** `TagFacetChips` solely owns the chip markup, the `filterPill` rule set, the `selectedTags` toggle, and the `X`; only the surrounding surface differs (which tags it is handed, plus the cap, the expander, and the `role="group"` / `aria-label="Filter by tag"` wrapper).
  - **Which surface owns the facet is one boolean** — `useMediaQuery('(max-width: 768px)')`, the complement of the stylesheet's `desktopQuery` — and the branches are mutually exclusive, so the chips and the `Filter by tag` landmark are in the document **exactly once at any width**; a duplicated landmark is as much a defect as a missing one. In jsdom the media query reports the desktop answer, so the unit suite exercises the ≥769px arrangement and `tag facet inside the compact filter disclosure` stubs it to the compact answer for the other.
  - **The `Filter (N)` count includes the tag selections** — active selector facets plus `selectedTagSet.size`, each facet contributing at most once — because the panel this trigger now contains the tags, and two active tags must not read `Filter (0)`. The trigger's emphasis reads that same number, and its accessible name stays the generic `Toggle filters`, which enumerates no facet and so cannot understate the panel.
