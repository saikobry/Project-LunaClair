# src/features/quiz-management/canvas/ — Quiz Canvas Authoring Sub-feature

## Purpose

Self-contained authoring subsystem for the quiz canvas builder (Google Forms-style editing of a quiz's questions), rendered on the dedicated `quiz-canvas` app-shell route. Owns its own state model (`QuizDraft` + `tempId`-keyed mutations), lifecycle orchestration (draft seeding, crash recovery, 3-layer save model), motion engine (accordion physics, drag reorder, toolbar chase/pinning), and debug tooling (`?pinviz=1` overlay). Recognized as a sub-feature boundary: its components, hooks, and tooling are tightly coupled, and only `QuizCanvasBuilder` crosses the boundary (consumed directly by `AppShell` as `canvas/QuizCanvasBuilder` — no barrel).

## Local Contracts

### Boundary & Save

- Public boundary: only `QuizCanvasBuilder` may be imported from outside `canvas/` — `AppShell` consumes it via the direct path (no barrel, per ADR-010). Enforcement is by convention (no lint gate), matching the feature's other import rules
- Import direction: canvas may import `../editors/*`, `shared/`, `app/` (providers), `application/`, and `domain/` — never `../components` (bank/catalog) or `../hooks` (bank/catalog hooks)
- 3-layer save model: (1) canvas state in `useQuizCanvas`, (2) autosaved `QuizDraft` in Dexie `quizEditingDrafts` via shared `useDraftAutosave` (2s debounce / blur / unload / 30s max throttle), (3) explicit Save Quiz → `SaveQuizUseCase` atomic transaction. The Question Bank and Quiz Catalog are only written on explicit save; drafts exist purely for crash recovery
- Question Bank is the single source of truth: imported canvas cards reference `questionId`; editing them updates the bank question on save and bumps `questionVersion` when prompt/payload content changes (points/order/metadata never bump). Bank-linked cards cannot change type. Duplicated cards detach from the bank (new question on save)
- After save success, `useQuizCanvasEditor` deletes the local draft, invalidates `['assessment']` caches, and rebinds the session to the saved `quizId`

### Toolbar Lane

The single canonical statement of the chase/pin algorithm. Reads: `QuizCanvasToolbarLane.tsx` (the loop), `QuizCanvasQuestionList.tsx` (resting heights), `utils/toolbarMath.ts` (pure math).

- **Motion ownership.** Canvas motion is GSAP- and CSS-owned. Do not mix React state-driven layout animation into the accordion, drag, or chase systems; GSAP tweens only `scale`/`y`/`zIndex` and never `box-shadow` (card shadows are the CSS-owned `cardActive` / `cardDragging` classes, transitioned by the card, so classes are never overridden by inline styles)
- **Window-scroll invariant.** The page owns the scroll, so the toolbar's visible pinning box is always inset-derived — **`topInset` → `innerHeight − bottomInset`** — never a scroller element's rect. `topInset` is the sticky header's measured height; `bottomInset` is the shell's bottom-bar inset (the mobile bottom nav at ≤768px, measured by `AppShell` from `main`'s own declared bottom padding — 0 above 768px and in Focus Mode) threaded down `QuizCanvasBuilder` → `QuizCanvasQuestionList` → lane, so a bottom-pinned toolbar stays above the bar. Tuned geometry: at 700×900 it lands 32px above the nav top (796 vs 828) — re-verify with a probe if the header/main relationship changes
- **Resting-position chase.** The loop glides the toolbar to a COMPUTED CONSTANT resting top — where the active card's top *will* be once every card above it is at its resting (collapsed) height — never the live mid-animation rect. Per-card resting heights come from `QuizCanvasQuestionList`'s self-healing `collapsedHeightsRef` (sampled in `settleLayout` for inactive, error-free cards; callout mount/unmount re-samples via the wrapper `ResizeObserver`), with `COMPACT_HEIGHT` as the never-sampled fallback, plus the deterministic error-callout estimate from the `errors` prop (see `utils/toolbarMath.ts`; the drift-verify phase corrects it). During a transition the loop issues ONE long glide (`0.35s` `power2.out`, matching the collapse duration) to that constant target, so the toolbar and the card arrive together — no dip/wobble, no wait, no timing bet
- **Keep-pace mode.** While the user is actively scrolling (speed > `SCROLL_NOISE`), the loop re-targets the card's LIVE position every frame with a velocity-scaled duration (down to `MIN_FOLLOW_DURATION`), so a fast fling never leaves the toolbar trailing a stale glide. Velocity is `readVelocity` (decaying, so it winds down rather than snapping)
- **Drift-verify.** Once the live layout holds still for 6 frames, reality wins: the loop corrects any residual estimate error with short snappy nudges, then stops polling
- **Loop wake & suspend.** Wakes on a `ResizeObserver` on the target node, the title card (meta growth moves the grid), the wrapper/grid, a `window resize`, and a **structural-move wake** — `wakeTick`, bumped when the active card's slot index changes (toolbar Move up/down, or an insert/delete above the card). That last one is required because reorders only MOVE card wrappers via GSAP `y`: a `ResizeObserver` fires on size, not position, so a moved card shifts the resting target without changing any observed box. Suspends (freezes) while a card is dragged; re-runs on release and glides to the resting target at the new slot
- **Scroll pinning uses a scroll + rAF geometry evaluator, deliberately NOT IntersectionObserver.** The IO alternative is rejected for two measured reasons: it watches the CARD's rect, but the toolbar is far shorter than an expanded card, so a card-based trigger fires too late on exit (toolbar fully clipped while the card still "intersects") and unpins too early (40px card overlap while the toolbar is still mostly clipped); and an IO cannot express a hypothetical rect for a wrapper whose real rect is meaningless while `position: fixed`. The evaluator computes the toolbar's would-be anchored footprint — the active card's RESTING doc-space top (the same constant the chase targets: collapsed-height cache + callout estimate, clamped like the chase) plus the toolbar's own height — against the viewport's visible box, and pins to the visible-box edge (viewport-relative but inset-aware: `topInset + PIN_MARGIN` / `innerHeight − effectiveBottom + PIN_MARGIN`, with `left` captured so the toolbar stays in its lane column)
- **Hysteresis.** The toolbar pins the moment the footprint's LEADING edge would leave the visible box — a true sticky trigger, so it is already pinned when it would start scrolling out. Unpin requires the footprint to fully clear BOTH edges by the 40px `PIN_REENTER` margin (symmetric full-fit). The gap between the pin line (at the edge) and the gate (40px inside) is what prevents anchored↔pinned flip-flop. Scroll speed feeds only a short pin-anticipation lead (`MAX_PIN_LEAD` ≤ 32px, capped below `PIN_REENTER` so the hysteresis gap always holds), so a fast fling locks in while still at the edge instead of popping in from above (no brief header overlap)
- **Relaxed activation re-arm.** EXCEPTION to the strict gate: an activation re-arm (an `activeCardId` focus change, detected via `prevActiveCardIdRef`) runs its FIRST evaluation relaxed (zero gate margin, zero velocity lead) so the toolbar reacts to the click in the same frame — immediate unpin onto the newly-focused card when its footprint is anywhere fully visible, or a straight flip to the correct edge — instead of holding the old pin until the 40px margin clears. A deliberate click cannot flip-flop; only scroll stutter can, and scroll/resize ticks keep the strict gate
- **Structural-move re-arm.** The shared `wakeTick` also re-runs the pin decision against the NEW resting footprint. A move-up can pull the resting top above the pin line with NO scroll/resize/RO signal (reorders only MOVE wrappers), so without this the chase would glide the toolbar up past the header and clip instead of pinning at the edge
- **Pinned geometry refresh.** A `ResizeObserver` on the wrapper/grid/title re-reads pinned geometry whenever their boxes change (card/grid growth, recovery-banner mount, toolbar size), and a `window resize` listener re-reads it on every viewport size change. The `resize` listener is load-bearing for a case the RO structurally cannot catch: a width resize recenters the maxWidth-capped canvas body, sliding the lane horizontally while every observed box keeps its SIZE (RO only reports size) — verified in a headless probe: zero RO callbacks while the lane moved ~110px. The one lane movement NEITHER signal catches is the Focus Mode rail animation at capped widths (the rail tweens its layout width, firing no `resize` event, and the shifted canvas only MOVES the lane), so a bounded per-frame drift poll on every pinned re-arm samples the lane's rect until it settles (~0.35s + slack) and re-applies the pinned geometry. All reads are live post-layout rects, so the pinned `left`/`top`/`bottom` always match the moved lane
- **Pin modes and the unpin handoff.** While pinned the chase loop is suspended (`pinState`, mirrored locally so re-arms while pinned stay in sync with the DOM). Unpinning converts the pinned viewport position back into the chase's scroll-invariant content space (`docY = wrapperRect.top − bodyRect.top`, NO `scrollTop` term) so the chase glides from where the toolbar visually was instead of jumping; the return glide is owned by the chase re-arm, not an explicit tween
- **Pin settle animations.** Pinning is a CONTINUOUS LOCK (0.25s `power2.out` from the toolbar's current on-screen position — no fade, since the edge-touch trigger pins while it is already at the edge). The settle runs on transform `y` deliberately: `refreshPin` re-writes `top`/`bottom`/`left` on the `pinState` re-arm ~1 frame later, which would cut a `top`/`bottom` tween to a single frame, while transform `y` is untouched by the geometry writer. A pin-SIDE flip (top ↔ bottom) is the one case where the toolbar is NOT at the edge it pins to, so its settle duration scales with cross-viewport travel (distance / `PIN_GLIDE_SPEED`, capped at `REFLOW_DURATION`). The `−PIN_MARGIN` settle-start clamp applies to TOP pins only (the never-paint-above-the-header guarantee for violent-fling pin-ins), never to bottom pins — clamping a bottom pin's large negative `fromY` was what teleported the toolbar in one frame while the settle animated a 16px sliver
- **Inset-driven re-arms ANIMATE instead of re-reading.** A Focus Mode toggle at ≤768px flips `bottomInset` (detected by `prevBottomInsetRef`). That re-arm slides the bottom-pinned toolbar with the nav — one `bottom: newInset + PIN_MARGIN` layout write, then a TRANSFORM-`y` fromTo from the current visual spot to 0 (0.35s `power2.out`, matching the rail/pill motion language; direction falls out naturally, ±88px) — because the toggle is the busiest frame (document relayout + double render) and a per-frame `bottom` tween would stutter there. The tween fires only when the footprint still violates the NEW effective bottom (`willStayPinned` mirrors the evaluator's unpin gate EXACTLY — both edges + `PIN_REENTER` margin — so the two can only disagree if geometry changes between frames, which self-corrects on the next scroll); if the freed space revealed the card, the re-arm does nothing and the evaluator unpins next frame, the chase gliding back from the current visual spot (seamless, no jump). All OTHER re-arms (rail animation, banner mount, resize) keep the INSTANT `refreshPin` re-read
- **Mobile.** Below 640px the lane collapses, pin styles are cleared, and `pinState` resets to anchored so returning to desktop resumes the chase; the toolbar renders as a floating bottom glassmorphism bar

### Drag Reorder

- Reorder is per-card GSAP `Draggable` instances (grip trigger, direction-aware midpoint crossing with a small hysteresis margin) bounded by the whole outer canvas column — meta card zone + question grid + reserved bottom dropzone (`BOTTOM_BUFFER = 160`, the documented ~158px drag floor with no margin; do not trim further without a headless drag re-verify) — so any card, collapsed or expanded, can travel up past Q1's midpoint and down past the last card's midpoint to reach any slot
- Grabbing a handle auto-collapses the held card to its compact summary (`compactHeightFor` — the MEASURED height from `collapsedHeightsRef`, falling back to `COMPACT_HEIGHT = 116` for never-sampled cards, sized for an unclipped two-row collapsed card) the moment a drag begins, and re-renders active cards as clean collapsed summaries (`isDragging` → `effectiveIsActive`, no clipped editor), so it glides lightweight through tight compact steps; on release the physical push engine re-expands it to full editor view at its new slot
- GSAP re-measures the element bounds into each card's local space on every press, so no manual bounds refresh is needed
- After a real drag the trailing browser `click` is suppressed for ~150ms, scoped to the dragged card, so dropping never accidentally expands a card
- Do not reintroduce HTML5 drag-and-drop into `QuizCanvasQuestionList`; keyboard-accessible reordering lives in the active-card toolbar (Move up/down)

### Height Engine

- `QuizCanvasQuestionList` accumulates DOM heights synchronously inside a layout effect before paint, so expanding/collapsing cards never overlap, and glides cards between slots with GSAP tweens (`duration: 0.35`, `power2.out`). Opening a card tweens height from its last stable collapsed height to full editor height with frame-synced `onUpdate` repositioning, so lower cards are physically pushed in real time
- The wrapper `ResizeObserver` routes in-flight height tweens — a card accordion tween OR the active card's nested metadata drawer (registered via the shared `heightAnimRef`) — through the same cheap frame-synced `applyPositions(false)` instant-push (no React re-render per frame); it settles only when no tween is running and nothing is dragged (the drag-collapse glide is owned by `onDragStart`'s `applyPositions(true)`). A drawer registers its `tempId` for the tween's duration and releases it on complete, interrupt, AND unmount (killing the in-flight tween), so a collapsed card's accordion tween is never blocked
- Never use `clearProps: 'height'` to end a height tween (see the drawer's Ownership row)

### Scroll-to-View

- Community-validated: the toolbar stays PINNED while its target card can scroll off-screen, so structural actions are feedback-less unless the viewport follows
- ADD always scrolls (`focusCard`, unconditional — the card did not exist a moment before, so there is no viewport position to preserve)
- MOVE UP/DOWN, DUPLICATE, and DELETE scroll CONDITIONALLY (`focusCardIfOffScreen`): the affected card (for delete: the card that slides into the vacated slot, or the title card when the quiz empties) is measured AFTER the 0.35s accordion reflow settles, and scrolls to center only when >80% of its height is clipped — a fully visible card is never scrolled, so rapid reordering never yanks the viewport
- `duplicateItem` returns the copy's `tempId`, pre-generated BEFORE the functional state update so the return is synchronous, so the toolbar can target the copy

### Authoring Rules

- **Meta card settings accordion rule** (community-validated): settings that are OFF-BY-DEFAULT and inert until enabled (timed, shuffle, retakes, …) go in a collapsed accordion inside the meta card, mirroring the answer-feedback drawer's GSAP height animation; settings that are ALWAYS-ACTIVE and consequential (passing percentage — a required, defaulted field whose value governs pass/fail) stay always visible with their helper line. Passing percentage must NOT be folded into an accordion. The meta card currently has zero off-by-default settings, so no accordion exists yet — build it when the first opt-in setting arrives
- **Pass-threshold boundary** (community-validated): the grading ENGINE grades by points (`AssessmentService`: `earnedPoints / maxPoints`), the author EDITS in percentage (the stored `passingPercentage`), and everything else the UI shows is a DERIVED, READ-ONLY translation of that same computation — never a second editable representation. The meta card's helper line is points-aware (`"Learners need to earn X of Y points (Z%) to pass"`, `X = ceil(passingPercentage/100 × totalPoints)`, falling back to the plain percentage when the canvas has 0 questions). Do NOT add a count-based ("N of M questions") threshold UI — it is a false statement whenever question points are mixed — and do NOT switch grading to count-based as a UI fix; that would be a separate domain-model decision
