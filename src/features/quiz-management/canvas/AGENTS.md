# src/features/quiz-management/canvas/ — Quiz Canvas Authoring Sub-feature

## Purpose

Self-contained authoring subsystem for the quiz canvas builder (Google Forms-style editing of a quiz's questions), rendered on the dedicated `quiz-canvas` app-shell route. Owns its own state model (`QuizDraft` + `tempId`-keyed mutations), lifecycle orchestration (draft seeding, crash recovery, 3-layer save model), motion engine (accordion physics, drag reorder, toolbar chase/pinning), and debug tooling (`?pinviz=1` overlay). Recognized as a sub-feature boundary: its components, hooks, and tooling are tightly coupled, and only `QuizCanvasBuilder` crosses the boundary (consumed directly by `AppShell` as `canvas/QuizCanvasBuilder` — no barrel).

| `QuizCanvasToolbarLane.tsx` | Decoupled right toolbar lane component (rAF Follow Loop — Resting-Position Model): owns the positioning wrapper (`position: absolute; top: 0`) and glides the toolbar to a COMPUTED CONSTANT resting top — where the active card's top will be once every card above it is at its resting (collapsed) height — never the live mid-animation rect. Per-card resting heights come from `QuizCanvasQuestionList`'s self-healing `collapsedHeightsRef` (sampled in `settleLayout` for inactive, error-free cards; callout mount/unmount re-samples via the wrapper ResizeObserver) with `COMPACT_HEIGHT` as the never-sampled fallback, plus a deterministic error-callout estimate derived from the `errors` prop (message count/length — deliberately approximate, never a live measurement; the drift-verify phase corrects it). During a transition the loop issues ONE long glide (`0.35s` `power2.out`, matching the collapse duration) to that constant target, so the toolbar and the card arrive together with no dip/wobble, no wait, and no timing bet; while the user is actively scrolling (speed > `SCROLL_NOISE`) the loop runs KEEP-PACE mode — re-targeting the card's LIVE position every frame with a velocity-scaled duration (down to `MIN_FOLLOW_DURATION`), so a fast fling never leaves the toolbar trailing a stale glide; once the live layout holds still for 6 frames, reality wins and the loop corrects any residual estimate error with short snappy nudges, then stops polling. Idle wake: `ResizeObserver` on the target node + the title card (meta growth moves the grid) + `window resize`, plus a structural-move wake — an effect re-arms the loop when the active card's slot index changes (toolbar Move up/down, or insert/delete above the card), which shifts the resting target without changing `activeCardId` or any wrapper size (a ResizeObserver fires on size, not position). While a card is dragged the loop is suspended (toolbar frozen); on release it re-runs and glides to the resting target at the new slot. Scroll pinning: a scroll + rAF geometry evaluator (NO `IntersectionObserver` — it watches the CARD's rect, but the toolbar is far shorter than an expanded card, so a card-based trigger fires too late on exit (toolbar fully clipped while the card still "intersects") and unpins too early (40px card overlap while the toolbar is still mostly clipped); an IO also can't express a hypothetical rect for a wrapper whose real rect is meaningless while `position: fixed`). The evaluator computes the toolbar's would-be anchored rect — the active card's RESTING doc-space top (the same constant the chase's one-glide targets: collapsed-height cache + callout estimate, clamped like the chase) + the toolbar's OWN height — against the VIEWPORT's visible box — WINDOW-SCROLL mode: the page owns the scroll (scroll events on `window`, scrollTop = `window.scrollY`), and the visible box is inset-derived — `topInset` (the sticky header's height, measured by the builder) → `innerHeight − bottomInset` (a constant during layout transitions, so a focus change never produces a transient pin→unpin snap); when the hypothetical footprint's LEADING edge leaves the visible box minus a scroll-speed anticipation lead (`hypoTop < topInset + lead` for top-pin, `hypoBottom > effectiveBottom − lead` for bottom-pin, where `effectiveBottom = innerHeight − bottomInset` is the viewport's visible bottom minus the shell-supplied bottom-bar inset (the mobile bottom nav at ≤768px, measured by AppShell from `main`'s own declared bottom padding — 0 at >768px and in Focus Mode — and threaded down via `QuizCanvasBuilder` → `QuizCanvasQuestionList` → lane) — so a bottom-pinned toolbar stays ABOVE the bar, never under it (tuned geometry: at 700×900 it lands 32px above the nav top — 796 vs 828 — re-verify with a probe if the header/main relationship ever changes), and is ALREADY pinned the moment it would start scrolling out of view, a true sticky toolbar) the toolbar pins to the visible box edge (viewport-relative but inset-aware — `topInset + PIN_MARGIN` / `innerHeight − effectiveBottom + PIN_MARGIN` — so a top-pinned toolbar locks just BELOW the sticky header, never over it, and a bottom-pinned one stays above the bar; `left` is captured so the toolbar stays in its lane column) so its actions stay reachable. Geometry-based side decision (which edge the footprint is leaving); scroll speed only feeds a short pin-anticipation lead (`MAX_PIN_LEAD` ≤ 32px, capped below `PIN_REENTER` so the hysteresis gap always holds) so a fast fling locks the toolbar in while it is still at the edge instead of popping it in from above (no brief header overlap); unpin requires the footprint to fully clear both visible edges by the 40px `PIN_REENTER` margin (symmetric full-fit), and the gap between the pin line (at the edge) and the gate (40px inside) is the hysteresis that prevents anchored↔pinned boundary flip-flop — EXCEPTION: an ACTIVATION re-arm (an `activeCardId` focus change, detected via `prevActiveCardIdRef`) runs its FIRST evaluation relaxed (zero gate margin + zero velocity lead) so the toolbar reacts to the click in the same frame — immediate unpin onto the newly-focused card when its footprint is anywhere fully visible, or a straight flip to the correct edge — instead of holding the old pin until the 40px margin clears (a deliberate click cannot flip-flop; only scroll stutter can, and scroll/resize ticks keep the strict gate). A STRUCTURAL-MOVE re-arm (the shared `wakeTick`, bumped when the active card's slot index changes — Move up/down or an insert/delete above it — and on idle wakes) re-runs the decision against the NEW resting footprint: a move-up can pull the resting top above the pin line with NO scroll/resize/RO signal (reorders only MOVE card wrappers via GSAP `y`; a ResizeObserver fires on size, not position), so without the re-arm the chase would glide the toolbar up past the header and clip instead of pinning at the edge. While pinned the chase loop is suspended (`pinState`, mirrored locally so re-arms while pinned — activeCardId swap, drag release, Focus Mode toggle — stay in sync with the DOM); unpinning converts the pinned viewport position back into the chase's scroll-invariant content space (`docY = wrapperRect.top − bodyRect.top`, NO scrollTop term) so the chase glides from where the toolbar visually was instead of jumping — the unpin handoff is seamless (docY = current visual position) and the return glide to the card is owned by the chase re-arm, not an explicit tween. Pinning is a CONTINUOUS LOCK (0.25s `power2.out` ease from the toolbar's current on-screen position into the pinned position — no fade, since the edge-touch trigger pins while the toolbar is already at the edge; the settle runs on transform `y` deliberately, because `refreshPin` re-writes `top`/`bottom`/`left` on the `pinState` re-arm ~1 frame later, which would cut a top/bottom tween to a single frame, while transform `y` is untouched by the geometry writer). A pin-SIDE flip (top ↔ bottom) is the one case where the toolbar is NOT at the edge it's pinning to — the settle duration scales with the cross-viewport travel (distance/`PIN_GLIDE_SPEED`, capped at `REFLOW_DURATION`) so the toolbar visibly glides between edges instead of whipping; the `−PIN_MARGIN` settle-start clamp applies to TOP pins only (the never-paint-above-the-header guarantee for violent-fling pin-ins), never to bottom pins — clamping a bottom pin's large negative `fromY` (a top→bottom flip) was what teleported the toolbar in one frame while the 0.25s settle animated a 16px sliver. Pinned geometry refresh: INSET-DRIVEN re-arms (a Focus Mode toggle at ≤768px flips `bottomInset` — the `prevBottomInsetRef` detects them) ANIMATE the bottom-pinned toolbar's offset instead of re-reading it — one `bottom: newInset + PIN_MARGIN` layout write, then a TRANSFORM-y fromTo from the toolbar's current visual spot to 0 (0.35s power2.out, matching the rail/pill motion language; direction falls out naturally, ±88px) so the toolbar slides up/down with the nav instead of snapping — the slide is on `y`, NOT `bottom`, because the toggle is the busiest frame (document relayout + double render) and a per-frame `bottom` tween would stutter there, and because `refreshPin` re-writes top/bottom/left on the `pinState` re-arm ~1 frame later (which would cut a bottom tween to a single frame) while transform `y` is untouched by the geometry writer; the tween only fires when the footprint still violates the NEW effective bottom (`willStayPinned` mirrors the evaluator's unpin gate EXACTLY — both edges + PIN_REENTER margin — identical math, so the two can only disagree if the geometry changes between frames, which self-corrects on the next scroll) — if the freed space revealed the card, the re-arm does nothing and the evaluator un-pins next frame, the chase gliding the toolbar back to its card from its current visual spot (seamless, no jump). All other re-arms (rail animation, banner mount, resize) keep the INSTANT `refreshPin` re-read: a `ResizeObserver` on the wrapper/grid/title re-reads it whenever their boxes change (card/grid growth, recovery-banner mount, toolbar size) AND a `window resize` listener re-reads it on every viewport size change — a width resize recenters the maxWidth-capped canvas body, sliding the lane horizontally while the observed boxes keep their SIZE (ResizeObserver only reports size, so it never fires for this — verified in a headless probe: zero RO callbacks while the lane moved ~110px and the pinned toolbar stayed behind), making the window `resize` event the reliable signal. The one lane movement NEITHER signal catches is the Focus Mode rail animation at capped canvas widths: the rail tweens its layout width (no `resize` event fires) and the shifted canvas only MOVES the lane without resizing any observed box — so a bounded per-frame drift poll on every pinned re-arm samples the lane's rect until it settles (~0.35s + slack) and re-applies the pinned geometry, keeping `left` glued to the lane; without it the pinned toolbar keeps its pre-animation `left` and visually escapes the lane. All reads are live rects post-layout, so the pinned `left`/`top`/`bottom` always match the moved lane. On mobile (<640px) the lane collapses, pin styles are cleared, and `pinState` resets to anchored so returning to desktop resumes the chase; the toolbar renders as a floating bottom glassmorphism bar |

## Local Contracts

- Public boundary: only `QuizCanvasBuilder` (`canvas/QuizCanvasBuilder.tsx`) may be imported from outside `canvas/` — `AppShell` consumes it via the direct path (no barrel, per ADR-010). Canvas internals (state, lifecycle, motion, tooling) must not be imported from outside `canvas/`. Enforcement is by convention (no lint gate), matching the feature's other import rules
- Import direction: canvas may import `../editors/*` (shared type editors), `shared/`, `app/` (providers), `application/`, and `domain/` — never `../components` (bank/catalog) or `../hooks` (bank/catalog hooks)
- 3-layer save model: (1) canvas state in `useQuizCanvas`, (2) autosaved `QuizDraft` in Dexie `quizEditingDrafts` via shared `useDraftAutosave` (2s debounce / blur / unload / 30s max throttle), (3) explicit Save Quiz → `SaveQuizUseCase` atomic transaction. The Question Bank and Quiz Catalog are only written on explicit save; drafts exist purely for crash recovery
- Question Bank is the single source of truth: imported canvas cards reference `questionId`; editing them updates the bank question on save and bumps `questionVersion` when prompt/payload content changes (points/order/metadata never bump). Bank-linked cards cannot change type. Duplicated cards detach from the bank (new question on save)
- After save success, `useQuizCanvasEditor` deletes the local draft, invalidates `['assessment']` caches, and rebinds the session to the saved `quizId`
- Canvas motion is owned by GSAP & CSS: `Draggable` for drag reorder (direction-aware midpoint crossing swaps with hysteresis; bounded by the whole outer canvas column element (meta card headroom above Q1, question grid, reserved bottom dropzone `BOTTOM_BUFFER = 160`); GSAP re-measures the element bounds into each card's local space on every press, so any card — collapsed or expanded — can swap into any slot end-to-end without forced height clipping; dragging auto-collapses the held card to its compact summary (`compactHeightFor`: measured `collapsedHeightsRef` height, `COMPACT_HEIGHT = 116` fallback) and re-renders active cards as clean collapsed summaries (`isDragging` → `effectiveIsActive`, no clipped editor) so it glides lightweight through tight compact steps; drag/active card shadows are CSS-owned classes (`cardActive` / `cardDragging`), so GSAP tweens only scale/zIndex and never `box-shadow`, and on release the physical push engine re-expands it to full editor view at its new slot; after a real drag the trailing browser `click` is suppressed for ~150ms, scoped to the dragged card, so dropping never accidentally expands a card; the active-card toolbar is a `toolbarLane` sibling whose position wrapper (`position: absolute; top: 0`) runs a rAF follow loop that glides to a computed RESTING target — the active card's top at all-resting heights: per-card collapsed-height cache (`collapsedHeightsRef`, sampled at `settleLayout` for inactive error-free cards) + `COMPACT_HEIGHT` fallback + a deterministic error-callout estimate from the `errors` prop — issuing ONE `0.35s` `power2.out` glide during the transition (toolbar and collapse arrive together: no chasing a moving rect, no dip/wobble, no timing bet), keep-pace mode re-targets the live position with velocity-scaled durations while the user is actively scrolling; then a drift-verify phase trusts the live position once the layout settles and nudges residual estimate error with short tweens; the loop settles after 6 stable frames, wakes on `ResizeObserver` (target + title card)/`window resize` or an active-card slot change (Move up/down, insert/delete above — reorders don't resize wrappers, so RO alone never fires), and suspends (freezes) while dragging; scroll pinning: a scroll + rAF geometry evaluator (no `IntersectionObserver` — the toolbar is far shorter than an expanded card, so a card-based trigger fires too late, and an IO can't express the wrapper's hypothetical rect) computes the toolbar's hypothetical anchored footprint (the card's RESTING doc-top + own height, clamped like the chase — a constant during layout transitions, so a focus change never causes a transient pin→unpin snap) against the viewport's visible box (window-scroll mode: `topInset` → `innerHeight − bottomInset`); the toolbar pins when the footprint's LEADING edge leaves the visible box minus a scroll-speed anticipation lead (`hypoTop < topInset + lead` / `hypoBottom > effectiveBottom − lead`, the viewport bottom minus the shell-supplied bottom-bar inset — already pinned the moment it starts to leave, sticky-style trigger) via `position: fixed` in the lane column — geometry-based side decision (scroll speed only feeds the lead and the velocity-scaled keep-pace chase), unpin requires the footprint to fully clear both visible edges by the 40px `PIN_REENTER` margin (symmetric full-fit; the gap between the edge and the gate is the hysteresis against boundary flip-flop — except for ACTIVATION re-arms, whose first evaluation runs relaxed (zero margin/lead, via `prevActiveCardIdRef`) so the toolbar reacts to a card click immediately instead of holding the old pin until full-fit, and STRUCTURAL-MOVE re-arms — the same slot-change `wakeTick` that wakes the chase — which re-run the decision against the NEW resting footprint so a move-up that pulls the resting top above the header pins at the edge instead of clipping (reorders fire no scroll/resize/RO signal)), chase suspended while pinned and resumed on unpin (viewport position converted to scroll-invariant content-space `docY = wrapperRect.top − bodyRect.top` so the chase glides, no jump), pinned geometry refreshed by a wrapper/grid/title `ResizeObserver` + `window resize` (viewport size changes, banner mount, card/grid growth) plus a bounded drift poll on pinned re-arms (the Focus Mode rail animation moves the lane without a resize event or any observed box size change)), tweens for accordion reflow, and frame-synced physical-push height tweens for expand/collapse (card height animates from its last stable snapshot while `onUpdate` repositions lower cards each frame). Do not reintroduce HTML5 drag-and-drop into `QuizCanvasQuestionList`; keyboard-accessible reordering lives in the active-card toolbar (Move up/down)
- WINDOW-SCROLL invariant: the page owns the scroll, so the toolbar's visible pinning box is always inset-derived (`topInset` → `innerHeight − bottomInset`), never a scroller element's rect
- Meta card settings accordion rule (community-validated): settings that are OFF-BY-DEFAULT and inert until enabled (timed, shuffle, retakes, …) go in a collapsed accordion inside the meta card, mirroring the answer-feedback drawer's GSAP height animation; settings that are ALWAYS-ACTIVE and consequential (passing percentage — a required, defaulted field whose value governs pass/fail) stay always visible with their helper line. Passing percentage must NOT be folded into an accordion. The meta card currently has zero off-by-default settings, so no accordion exists yet — build it when the first opt-in setting arrives
- Pass-threshold boundary (community-validated): the grading ENGINE grades by points (`AssessmentService`: `earnedPoints / maxPoints`), the author EDITS in percentage (the stored `passingPercentage`), and everything else the UI shows is a DERIVED, READ-ONLY translation of that same computation — never a second editable representation. The meta card's helper line is points-aware (`"Learners need to earn X of Y points (Z%) to pass"`, `X = ceil(passingPercentage/100 × totalPoints)`, falling back to the plain percentage when the canvas has 0 questions). Do NOT add a count-based ("N of M questions") threshold UI — it is a false statement whenever question points are mixed — and do NOT switch grading to count-based as a UI fix; that would be a separate domain-model decision
- Scroll-to-view rule (community-validated): the toolbar stays PINNED while its target card can scroll off-screen, so structural actions are feedback-less unless the viewport follows. ADD always scrolls (`focusCard`, unconditional — the card did not exist a moment before, so there is no viewport position to preserve). MOVE UP/DOWN, DUPLICATE, and DELETE scroll CONDITIONALLY (`focusCardIfOffScreen` in `useQuizCanvasEditor`): the affected card (for delete: the card that slides into the vacated slot, or the title card when the quiz empties) is measured AFTER the 0.35s accordion reflow settles, and scrolls to center only when >80% of its height is clipped — a fully visible card is never scrolled, so rapid reordering never yanks the viewport. `duplicateItem` returns the copy's `tempId` (pre-generated BEFORE the functional state update so the return is synchronous) so the toolbar can target the copy
