# src/application/ — Application Layer

## Purpose

Framework-agnostic use cases coordinating domain contracts between React adapters and infrastructure.

## Ownership

- `use-cases/quiz/` owns quiz session start (`StartQuizSessionUseCase`), atomic evaluation & submission (`SubmitQuizSessionUseCase`), and session abandonment (`AbandonQuizSessionUseCase`).
- `use-cases/quiz-management/` owns question and quiz authoring workflows, including `SaveQuizUseCase` (concurrency guard → draft validation → version increment rules → atomic commit via `QuizEditorService`, returns the `SaveQuizResult` discriminated union) and the two Question Bank writes `CreateQuestionUseCase` / `UpdateQuestionUseCase`, which are **validating boundaries** returning the same `{ success, errors }` shape (see Local Contracts).
- `use-cases/library/` owns material create/update/touch workflows and the **single** removal workflow (`RemoveMaterialUseCase` — local-only removal of a material, delegating to the atomic cascade that clears the material row along with its questions, quizzes, document content, collection membership, and stored assets). There is no row-only delete use case by design — `LibraryRepository` exposes no delete, so a material row cannot be removed without its dependents. Library population happens via `use-cases/package/ImportStudyPackageUseCase` and `use-cases/sharing/ClonePublishedShareUseCase` — the catalog-era single/batch material import use cases were removed in the Phase 5 catalog retirement.
- `use-cases/reader/` owns annotation persistence workflows (`SaveHighlightUseCase`, `SaveDrawingUseCase`, `ClearAnnotationsUseCase`).
- `use-cases/content/` owns document content persistence workflows (`UpdateDocumentContentUseCase` — updates local markdown representation in Dexie without coupling to UI features or library discovery).
- `use-cases/flashcards/` owns spaced-repetition review state transitions and persistence coordination (`RecordFlashcardReviewUseCase`) and review-state **invalidation** (`ResetFlashcardReviewsUseCase` — a two-phase bracket a question write is wrapped in from the outside: `capture(questionIds)` reads the pre-write rows, keeping only `fill_in_blank` questions (the only kind with per-blank keys), and `execute({ before })` runs after the write, resolving the post-write rows and asking the pure `domain/flashcards/engines/clozeReviewReset` predicate which blank indices the edit invalidated before deleting exactly those keys through `FlashcardReviewRepository`. The predicate judges an edit by the **resolved card front** (`domain/flashcards/engines/clozeCardFront` — the same function the projection renders), so a reworded generic prompt clears nothing and a real prompt change clears every blank. **The policy is content-based, deliberately NOT version-based** — `version` increments on every update, publish and archive included, so keying off it would wipe a question's study history every time it was published. The pre-write read is what makes a partial `UpdateQuestionInput` safe: a difficulty-only save supplies no payload, so the post-write row is identical and nothing is invalidated, rather than the reset running unconditionally. **Known limitation, deliberately not fixed: the bracket is not durable.** If the question write succeeds and the deletion then fails, nothing records the pending invalidation and a retry re-captures the already-edited row — `before` and `after` come back identical, so the invalidation is lost permanently and the retry is **not** self-healing. Recovering it needs a durable pending-reset record, a real change to this use case; the current behaviour is pinned by `__tests__/ResetFlashcardReviewsUseCase.test.ts` so fixing it is a visible act. The authoring use cases never call it — quiz-management knows nothing about review state, so both write paths (`SaveQuizUseCase` in the quiz canvas, `UpdateQuestionUseCase` in the Question Bank) invoke the reset **alongside** the save, from the composition that already calls them. Every deletion goes through `FlashcardReviewRepository.deleteByKeys`, whose adapter tombstones into the sync outbox; there is no tombstone-free path.
- `use-cases/analytics/` owns analytics coordination workflows (`GetGlobalAnalyticsUseCase`, `GetMaterialAnalyticsUseCase` — delegates raw data aggregation and calculations via `AnalyticsRepository` port). They are pure pass-throughs over the port: the card-maturity pool, the orphan diagnostic, and the forecast scoping all live in `domain/analytics/`, so a use case never derives a card count, never absorbs an orphan, and never throws over one.
- `use-cases/ai/` owns AI prompt/context orchestration, streamed chat execution with atomic turn persistence (`SendChatMessageUseCase` — stamps the persisted turn with the provider's token usage and the model that served it, on failed turns as well as completed ones; resolves grounding via `AiGroundingResolver` from thread state, attaching document markdown capped to the serving model's budget via `AiContextBuilder`; opens the turn atomically via `AiChatRepository.saveMessagePair` with a streaming placeholder), next-request grounding estimation (`GetAiGroundingContextUseCase` — shares `AiGroundingResolver` to return character counts and mode for the context meter without leaking document text), thread grounding mutation (`SetThreadGroundingUseCase` — partial update, rejecting 'whole' for global threads), new-conversation default preference (`SetGroundingDefaultUseCase` — device-local preference), selection-thread preference (`SetSelectionThreadModeUseCase` — latest vs distinct conversation for reader selection actions, device-local), preferred-model preference (`SetPreferredModelIdUseCase` — next-request model choice, device-local), and conversation-session lifecycle management (`ResolveAiThreadUseCase` — recovers turns abandoned mid-stream and resolves the newest session in scope without ever creating one; `CreateAiThreadUseCase` — always inserts a distinct session with thread grounding initialized from preference, rejecting 'whole' for global threads; `RenameAiThreadUseCase` — retitles a session without touching `updatedAt`, so recency keeps tracking conversation activity rather than edits; `GetAiThreadMessagesUseCase`, `DeleteAiThreadUseCase`, `ClearChatHistoryUseCase`). Sessions are scoped to a material and are local-only.
- `use-cases/ai/GetAiModelCatalogUseCase` resolves the model catalog the UI should offer, delegating the fetch/cache/bundle merge to the `AiModelCatalogRepository` port. It is the application-layer seam that keeps features out of infrastructure; the repository owns the fallback chain, so callers never handle a catalog failure.
- `use-cases/generator/` owns AI structured content synthesis workflows (`GenerateQuestionsUseCase`, `BatchCreateQuestionsUseCase`) coordinating `AiService.generateStructured`, section-bounded context extraction, strict domain draft validators, and atomic batch persistence to `QuestionRepository.createQuestionsBatch` with default `status: 'draft'`. **There is one generation pair and one draft type.** A generated flashcard is a `fill_in_blank` question, not a second record: `questionToCards` projects a cloze into one card per blank, each with its own SM-2 schedule, so the retired `GenerateFlashcardsUseCase` / `BatchCreateFlashcardsUseCase` pair (which stamped every card `type: 'identification'`, hardcoded `difficulty: 'medium'`) no longer has a role to play. The generation use case takes the shared **`AiGroundingResolver`**: the source document is resolved from the request's `materialId` (never supplied by a caller), the model's `maxOutputTokens`/`maxDocumentContextChars` supply the budgets, the resolved model id is forwarded to the provider, and a material with no readable content fails as `EMPTY_DOCUMENT` instead of prompting on empty text. `execute` returns `DraftBatch<GeneratedQuestionDraft>` (`{ drafts, rejected }`) rather than a bare array: the valid drafts are kept and the malformed ones are reported, so the dialogs can name the shortfall instead of silently returning fewer items. The system prompt is assembled per request — schemas for **only** the requested `types` are included (unused formats are more for the model to imitate, lengthen the prompt, and the tail of a long output is where it degenerates), the rules name the failure modes actually observed from the default model (a dropped `true_false` prefix, an omitted `correctIndex`), and a **CLOZE ATOMICITY rule is emitted only when `fill_in_blank` is among the allowed types** — that is where the retired card prompt's one real strength (one discrete fact per blank) now lives. Both `blanks`/`correctAnswer` prompts ask for **2-4 subject-matter topic tags** per item and rule out provenance tagging; `BatchCreateQuestionsUseCase` persists `draft.tags` as-is — tags stay filterable classification, and persistence stamps no marker of its own, so a generated row is classified by what it is about rather than by how it was authored. **The batch use case is a validating boundary, not a trust boundary.** It is the single writer for generated batches, so it re-runs the domain's own `validateQuestionDraft` on every draft instead of writing `draft.payload` verbatim on the assumption that someone upstream checked. Without that gate the cloze guarantee is a *convention*: a `___`-less template carries no marker, so `questionToCards` silently falls back to one whole-question card and the per-blank schedules never appear — no error, just a worse study surface. Re-validating **cannot double-report**: `GenerateQuestionsUseCase` hands over only drafts that already passed that same validator, so on the live path every draft passes again and the generator's own `rejected` list is a disjoint population (those items never arrive). The only drafts the boundary can refuse are ones that reached it *without* passing first. Failure follows the generator's **salvage** policy, never a throw and never a repair: the offending item is dropped, valid siblings are still persisted, and `execute` returns `BatchCreateQuestionsResult` (`{ created, rejected }`) so the drop is reportable rather than a silent shortfall — the same reason `GenerateQuestionsUseCase` returns `DraftBatch`. Repair is forbidden for the same reason the validator forbids it: a repaired blank would assert an answer nobody supplied.
- `use-cases/importer/` owns content extraction and import orchestration (`ExtractContentUseCase` — resolves format importer, executes extraction supporting both local Tesseract and AI Vision MAX with 12s pacing and rate-limit cooldown, applies multi-pass Markdown conversion, and catches `partialResult` upon abort/cancellation to construct a review candidate with partial markdown and `extraction.isPartial: true`; `CommitImportUseCase` — generates material/document IDs, sets metadata, persists original file blob to `localAssets` (the Dexie v14 store keyed by `assetId`, indexed by `materialId`), and atomically registers material with `materials` and `documentContents` stores; `CleanupImportWithAiUseCase` — opt-in AI markdown cleanup accepting `CleanupImportRequest` (`{ markdown, title, model, catalog, signal, onProgress }`); features an internal branch between single-pass (<= 9,000 chars) and section-aware chunking (> 9,000 chars, ~8,000 chars/chunk via `DocumentChunker`), extracts sentence-safe preceding snippets (`extractSafePrecedingSnippet` snapping to complete sentence boundaries within 500 chars) to prevent echo generation, hardens section prompts with anti-echo, vertical list, GFM pipe table conversion, list numbering protection, and page-transition boilerplate stripping instructions, enforces heading hierarchy preservation, isolated seam heading deduplication, and assembly seam safeguards (`assembleCleanedChunks` conservative proper-prefix prose dangling tail pruning and line/paragraph overlap trimming), applies 12s pacing and 429 rate-limit cooldown retries on MAX, supports mid-run failure recovery via `retryCleanupRemaining()` reusing cached sections, and emits granular `AiCleanupProgress` events).
- `use-cases/package/` owns study package materialization and import orchestration (`MaterializeStudyPackageUseCase` — extracts canonical material, questions, quizzes, and **every** stored asset of the material (via `AssetRepository.getByMaterialId`), strips personal learning/sync histories, assigns package-scoped `pkg_*` identifiers, numbers assets `pkg_asset_1..N` in a deterministic order (filename asc, asset id as tie-breaker) and rewires each `lc-asset://` URI by asset identity so a document's references stay paired with their own payload (legacy rows, whose `assetId` equals their `materialId` after the v14 migration, match the same rule); `ImportStudyPackageUseCase` — validates the package graph, executes collision-free ID remapping, and delegates atomic persistence to `StudyPackageImportService`). Material `tags` round-trip portably: materialization copies `material.tags` into the `PackageMaterial`, remapping copies them to the remapped material, and import stamps them onto the persisted `StudyMaterial`. **A malformed package THROWS and imports nothing — there is no tolerated-and-reported variant.** The validator is strict, so a structurally malformed question payload is one of its `errors`, the throw happens before the transaction opens, and a caller holding an `ImportStudyPackageResult` therefore holds a package whose every question payload is structurally valid for its type. `ImportStudyPackageResult` no longer carries `warnings`.
- `use-cases/sharing/` owns cloud package distribution, discovery, and cloning (`PublishStudyPackageUseCase` — materializes portable `StudyPackage`, **runs the strict client publish gate**, and publishes to cloud via `ShareTransport`; `FetchPublishedShareUseCase` — fetches remote published share snapshot and runs defense-in-depth domain validation; `ListPublicSharesUseCase` — coordinates public shares listing with pagination and search; `ClonePublishedShareUseCase` — orchestrates fetch → validate → remap → commit transaction → download telemetry tracking; `TrackShareDownloadUseCase` — records download increments; `DeletePublishedShareUseCase` — authorizes and deletes remote published shares).
- **The client publish gate: `validateStudyPackage(pkg)` runs locally before anything is published, in `PublishStudyPackageUseCase`, and again before a file is written, in `features/package/hooks/useExportStudyPackage`.** The Worker remains the server-side authority and refuses the same package, so the local call never replaces it — it is the local boundary the root `AGENTS.md` seeder invariant depends on, and it exists because `MaterializeStudyPackageUseCase` copies each question's payload **verbatim**: a question that arrived malformed from a legacy share is re-materialized exactly as malformed, so without the gate a malformed `.lcpack` is exported — and the Worker then only stops the *publish* after a round trip, leaving the user holding a file nobody can clone. The gate is the whole strict tier, not just payload shape, so it also refuses anything else the endpoint would reject. Its refusal is a thrown `Error` naming the first offending question, surfaced through each surface's existing error channel. It is deliberately **not** inside `MaterializeStudyPackageUseCase`, which `useStudyPackageSize` shares purely to measure bytes. Pinned by `use-cases/sharing/__tests__/PublishStudyPackageUseCase.test.ts` and `features/package/hooks/__tests__/useExportStudyPackage.test.tsx`, both of which fail if the call is removed.
- `use-cases/sync/` owns application sync workflows (`ResolveConflictDraftUseCase` — coordinates document divergence resolution with keep_server, keep_local, or merge strategies via `ConflictDraftRepository.resolveConflict`; `TriggerSyncUseCase` — triggers single-flight sync convergence; `GetSyncStatusUseCase` — surfaces current sync status and diagnostics; `GetConflictDraftsUseCase` — retrieves unresolved conflict drafts).
- `collections/` owns playlist-model collection workflows (`CreateCollectionUseCase` — validates title, assigns `max(order) + 1`; `UpdateCollectionUseCase`; `DeleteCollectionUseCase` — deletes collection AND removes its `collectionMaterials` junction rows; `AddMaterialToCollectionUseCase` — rejects duplicates, auto-calculates `max(order) + 1`; `RemoveMaterialFromCollectionUseCase`; `ReorderCollectionMaterialsUseCase`).
- `sync/` owns cloud synchronization convergence orchestration (`SyncEngine` coordinating the 4-step convergence cycle: pull → push outbox → pull catchup → finalize idle via `SyncReconciler` domain port), single-flight mutex (`syncMutex` merging concurrent calls and executing requested follow-up cycles), observable in-memory projection (`SyncStatusStore` with `rehydrateFromStorage` and reactive listeners), and exponential backoff retry policies (`syncRetryPolicy` / `calculateRetryDelay`). Browser lifecycle triggers (`online`, `visibilitychange`, timers) are decoupled into `BrowserSyncLifecycle` in infrastructure.
- `quiz-management/drafts/` owns the quiz canvas Application Session DTOs (`QuizDraft`/`QuestionDraft`), draft validation (`quizDraftValidation`), the `QuizDraftRepository` crash-recovery contract, and draft seeding helpers. Drafts carry UI session concerns (`tempId`, `isDirty`) and are never persisted to the Question Bank or Quiz Catalog. **`quizDraftValidation` is the canvas's validating write boundary, and it COMBINES two rules rather than owning either copy:** its own authoring rules (which field to fix, one message per field, keyed by `tempId` so the card renders them inline) run first, and a card they **accept** is then handed to `domain/quiz/validation/questionPayloadValidation` — the single owner, whose wording is a frozen contract the Worker mirrors. Two facts have no authoring rule and are caught only by that call: a `payload.type` disagreeing with the card's declared `type` (the UI lists and labels by the declared type, `questionToCards` dispatches on `payload.type`) and an `acceptedAlternatives` that is not an array of strings. Consulting the owner **only for a card the authoring rules accepted** is what keeps one defect from being reported twice in two vocabularies, and it is not a weaker gate — a card the authoring rules refuse is refused either way. A new authoring surface follows the same shape: call the owner, or be demonstrably outside its scope.

## Local Contracts

- Use cases and application services never import React, TanStack Query, Dexie, browser APIs, features, or UI components.
- `SyncEngine` encapsulates the 4-step sync convergence protocol (pull -> push batches -> pull -> finalize idle), enforces a single-flight mutex with follow-up cycle execution, handles offline detection gracefully, and updates `SyncStatusStore` through the `SyncReconciler` port.
- Dependencies are strictly domain repository/service contracts, domain models/services, and application input/output types.
- React hooks remain thin adapters for cache behavior and presentation concerns.
- `SaveQuizUseCase` never touches IndexedDB draft storage or query caches — draft deletion and cache invalidation belong to the UI editor layer. It also never touches flashcard review state: `ResetFlashcardReviewsUseCase` is invoked alongside the save, never from inside it. Its declared type at the composition root is narrowed to `Pick<SaveQuizUseCase, 'execute'>` because the app layer wraps it in the analytics cache-invalidation decorator (`src/app/bootstrap/analyticsInvalidation.ts`); the decorator is a plain object, not a subclass, and a use case must not gain private members a decorator would have to reproduce.
- **The Question Bank is a validating write boundary, and it was the last authoring surface that was not.** `CreateQuestionUseCase.execute` and `UpdateQuestionUseCase.execute` call `domain/quiz/validation/questionPayloadValidation` — the single owner of the rule — and return the same `{ success: true, question } | { success: false, errors: string[] }` shape `SaveQuizUseCase` uses, because a malformed answer payload is a **refusal the author has to see and fix**, not a thrown error: the editor is holding the content that would repair it. `errors` carries the validator findings verbatim, so each names the offending field without the UI re-deriving or re-wording the rule. This was a **call to the existing owner, not a third copy**; the module docstring had already recorded that a persistence-boundary copy was deliberately rejected in favour of one rule with several call sites, and the omission was that this boundary had none.
- **Two rules the gate is shaped by, both load-bearing.** (1) **A partial input carrying no `payload` is NOT gated.** `UpdateQuestionInput` is partial by contract — a publish, archive, or points-only save supplies none — and gating an absent payload would refuse a metadata edit over content the call is not writing. So the rule applies to a payload the write *actually supplies*, which is also exactly the repair path: a row that predates the gate is refused on the save that leaves it broken and accepted on the save that fixes it. (2) **The declared type is the STORED one, not the payload's own `type`.** `UpdateQuestionInput` carries no `type`, and the row's is the fact the payload is judged against — which is what makes the `payload.type` ↔ question-type agreement rule enforceable on this path at all. A missing row is left to `updateQuestion`, which owns that refusal and its message.
- **The editor keeps the dialog open on a refusal, and never runs the review reset around one.** `QuestionEditorDialog` awaits the write result, renders the findings in the same error-callout presentation the quiz canvas card uses for a `SaveQuizUseCase` refusal, and does not close or toast success. The refusal clears as soon as the author edits the answer. `useQuestionManagement.updateQuestion` skips the `ResetFlashcardReviewsUseCase` bracket's `execute` when the write is refused: nothing changed, so there is nothing to invalidate, and closing the bracket would bracket a write that never happened.
- **Why this mattered: the Bank's own default payloads are malformed for four of the five types, reachable by typing a prompt and nothing else** — `identification` `{correctAnswer: ''}`, `fill_in_blank` `{template: '', blanks: []}`, `multiple_select` `{correctIndices: []}`, `multiple_choice` `{choices: ['','']}`. The only gate in the chain was `isDisabled={!prompt.trim()}`. The consequences were already in users' libraries and none of them warned: a `fill_in_blank` with an empty template projects a card with an **empty back face** — permanently unanswerable, yet `buildCardKeyPool` counts it, so Insights' maturity bar and the 7-day forecast counted a card nobody can get right — and an `identification` with an empty answer graded **wrong forever**, silently.
- **Recording the gap, because a diff would otherwise close it silently.** Until this contract existed, the Question Bank was the only authoring surface with no payload validator anywhere in its chain. The gate is now present and pinned by `use-cases/quiz-management/__tests__/CreateQuestionUseCase.test.ts` and `UpdateQuestionUseCase.test.ts` (each asserting both halves: the finding names the field AND the repository is never reached), plus the repair-path case. **A new authoring surface must call the owner or deliberately not be one** — the omission here was invisible precisely because the rule already existed three times over elsewhere.
- Version increment rule: `questionVersion` bumps only when question prompt or answer payload content changes; points, order, and quiz-specific metadata never bump.
- **The payload comparison reads the STORED row, and both sides are now well-formed.** `payloadsEqual(a, b)` compares `a` = the persisted question against `b` = the draft item, and it reads both directly. The `Array.isArray` guards that used to sit here existed only because a package the READ tier tolerated could persist an `acceptedAlternatives` / `blanks` that was not an array, and reading one unguarded is a `TypeError` on a quiz the author is trying to re-save. **Every ingress to `db.questions` now validates, so the field is an array or is absent** — and `acceptedAlternatives` is optional, so `?? []` covers exactly the ordinary absence. This does not soften the bump rule: a stored value read as absent, and a draft supplying a real one, **is** a content change and still bumps. End-to-end reachability — real `validateStudyPackage` → real `ImportStudyPackageUseCase` → real canvas seeding → real save — is pinned in `use-cases/quiz-management/__tests__/SaveQuizUseCase.test.ts`, including a case proving a share carrying a non-array `acceptedAlternatives` is refused by the import and therefore never becomes a stored row.
