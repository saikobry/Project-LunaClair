# src/domain/ — Business Domain Models

## Purpose

Pure business domain models and logic — interfaces, types, and pure functions that describe the problem space. Domain modules must have zero React or UI dependencies.

## Ownership

Reserved domains:
- `reader/` — Document reading models, `DocumentRepository` and `AnnotationRepository` async contract interfaces, pure `parseAssetReference` (`utils/assetReference.ts` — syntax-only `lc-asset://{assetId}` extraction: returns the asset id, `undefined` for every other source; never queries storage and never sees `materialId`), `DocumentContentRepository` + `ImportedDocumentContent` (locally imported document markdown keyed by `documentId` — the explicit local representation of an imported material's content, distinct from the SW network cache), `DocumentNotFoundError` typed domain error, annotation value types (`annotation.types.ts`: `HighlightItem`, `DrawingPath`, `Point`, `HighlightColor`, `AnnotationMode`, `DrawingTool`)
- `quiz/` — Assessment engine: question models (5 types: `multiple_choice`, `multiple_select`, `true_false`, `identification`, `fill_in_blank`), canonical question-type metadata (`models/questionMetadata.ts` — the ordered `QUESTION_TYPES` list, `QUESTION_TYPE_LABELS` with the formal spellings (`Fill in the Blank`, `True / False`), and `VALID_QUESTION_TYPES`; the single owner of type knowledge, so a sixth type must supply its label at the definition site rather than at nine scattered consumers), quiz/session models, `virtualQuiz.ts` in-memory factory & deterministic question ordering, `QuestionRepository`/`QuizRepository`/`QuizSessionRepository` contracts (supporting multi-item/batch lookups, discriminated `CreateSessionInput`, and `getAllCompletedSessions` queries), per-type payload structural validation (`validation/questionPayloadValidation.ts` — pure, zero-dependency `validateQuestionPayload(declaredType, payload)` covering all five types: `multiple_choice`/`multiple_select` require at least two non-empty choices plus an in-range correct index/indices, `true_false` a boolean answer, `identification` a non-blank answer, and `fill_in_blank` an exact `___`-count / `blanks.length` parity; a `payload.type` that disagrees with the declared type is reported too. **It is the single owner of this rule with several call sites, not one rule per boundary**, and every ingress to `db.questions` now calls it: `validateStudyPackage` (import and publish), `SaveQuizUseCase` through `quizDraftValidation` (the canvas, which consults this owner for a card its own authoring rules accept), `CreateQuestionUseCase`/`UpdateQuestionUseCase` in the Question Bank, and `BatchCreateQuestionsUseCase` via `validateQuestionDraft`. The Worker mirrors the wording at publish time. See `src/application/AGENTS.md` → Local Contracts for the gate that made this true rather than conventional), strategy-pattern grading (`QuestionStrategy` + 5 implementations + `QuestionStrategyResolver`), pure `AssessmentService`. (Notes: the pure tag helpers live in `shared/utils/tags.ts` — they reference no domain model; the presentation badge palette lives in `features/quiz/utils/quizBadgeAppearance.ts`, re-exported for the authoring surfaces by `features/quiz-management/utils/quizBadgeAppearance.ts`).
- `library/` — Document/library models, `LibraryRepository` async contract interface with DTOs (`CreateMaterialInput`, `UpdateMaterialInput`) — `StudyMaterial` carries portable content `tags?: string[]` (optional in both DTOs) — and `LibraryImportService` application service contract, which is **removal-only** (`removeMaterial`: the material row, its questions/quizzes, its document content, its `collectionMaterials` junction rows, its `localAssets` rows, and its `flashcardReviews` schedules, in one transaction — removal must not strand blobs, stale collection membership, or review schedules). **The `importMaterial` / `importMaterialBatch` methods and the `ImportMaterialInput` type were deleted (Sep 2026):** the catalog-era import use cases that called them went in the Phase 5 catalog retirement, and a writer nothing can call is an *ungated* write surface into `db.questions` — a compatibility promise with no population behind it, so it was deleted rather than gated. Library population goes through the writers that validate (`StudyPackageImportService` for a cloned share or imported `.lcpack`, the importer use cases for a document)
- `assets/` — Local binary asset access: `StoredAsset` (canonical row: `assetId`, `materialId`, `blob`, `mimeType`, `filename`, `importedAt`) and the read-only `AssetRepository` port (`get(assetId)`, `getByMaterialId(materialId)`). Source-agnostic by design — an asset is a material asset whether it arrived from an `.lcpack` clone, a PDF/image import, or a future importer.
- `flashcards/` — Spaced repetition domain: `Flashcard` domain mapping derived from `Question` (`questionToCards` — a transient, never-persisted projection that is **1:1 for every non-cloze type and 1:N for `fill_in_blank`**, where each blank becomes its own card so each carries its own SM-2 schedule; discriminated by card **shape** (`kind: 'recall' | 'choice'`), never by the source question type), the card-key scheme (`cardKey.ts` — the single owner of the durable key formats review state is persisted under: `cardKeyForQuestion` builds `q:${questionId}` and `cardKeyForBlank` builds `q:${questionId}#${blankIndex}`; the `#` suffix is outside the question-id charset `[a-zA-Z0-9_-]`, so the two can never collide), the resolved cloze front (`clozeCardFront.ts` — `resolveClozeCardFront(prompt, template)`, **shared by the projection and the invalidation policy** so the two can never disagree about what a card says; `template` is typed `string` because every ingress validates, and an *empty* template is the one live case it normalises; see Local Contracts), pure SM-2 scheduler (`review`, `isDue`, `createInitialReviewState`), deck ordering (`orderDeck` — takes already-projected `Flashcard[]` so the caller owns card order), the cloze schedule-invalidation policy (`clozeReviewReset.ts` — `affectedClozeBlankIndices`, the pure content-based predicate naming which per-blank review keys a question edit retires; see Local Contracts), and `FlashcardReviewRepository` async contract interface (supporting `getByKeys`, `getByMaterial`, and `getAllReviews`)
- `analytics/` — Pure learning analytics engine: canonical view types (`analytics.types.ts`), local timezone calendar date utilities (`dateUtils.ts`), pure consecutive streak calculation with grace evaluation (`streakEngine.ts`), 365-day volume activity calendar generator (`activityEngine.ts`), topic mastery scoring with difficulty multipliers ($1.0, 1.5, 2.0$) and deterministic tie-breaking (`masteryEngine.ts`), the **projected card-key pool** (`cardKeyPool.ts` — `buildCardKeyPool(questions)`, the union of the card keys a set of in-scope questions projects, owned here so the global and per-material scopes cannot drift), mutually exclusive card maturity partition and review forecast (`retentionEngine.ts`), and global study overview metrics aggregation (`overviewEngine.ts` — takes the same projected card-key pool as a required parameter, so its current-workload figure cannot drift from the maturity breakdown; see Local Contracts)
- `ai/` — AI Tutor and study assistant domain.
  - **Canonical types.** `ai.types.ts` defines `AiChatMessage`, `AiChatRequest`, `AiGenerationRequest`, `AiStructuredOutputValidator<T>`, `AiGenerationError`, `AiStreamEvent`, `AiTutorMode`, `AiUsage`, `AiThread`, `AiGroundingMode`, `AiMessageRecord`, `AiMessageStatus`.
  - **Context extraction and assembly.** Pure markdown context extraction (`extractSectionContext.ts` bounding prompt tokens to headings/selections) and pure context assembly (`AiContextBuilder.ts` bounding document and selection character limits and sanitizing prompts).
  - **The model catalog** (`services/aiModelCatalog.ts`) is the client's bundled mirror of the Worker's public registry:
    - **Descriptor.** `AiModelDescriptor` (id, display, window, output reservation, document budget, `pricing: null` when free).
    - **Offline fallback.** `DEFAULT_AI_MODEL_CATALOG` is the fallback when no served catalog is known.
    - **Descriptor lookup.** Pure `findAiModelDescriptor` / `getAiModelDescriptor` resolve by catalog id **or** the provider model id older turns recorded.
    - **Version ordering and format.** `compareAiCatalogVersions` orders the `YYYY-MM-DD.N` label numerically field-by-field, so a malformed label can never outrank a well-formed one; `isAiCatalogVersion` is the format contract, asserted for both sides by the Worker's coherence test.
    - **Catalog shape and disabled state.** `isAiModelCatalog` validates the shape; `isAiCatalogDisabled` reads the deployment's `availability: 'disabled'`, which stops the assistant rather than emptying a picker.
    - **Model selection.** `resolveAiModelSelection` returns the selected descriptor, or `null` when there is nothing legitimate to send on — switched off, or a catalog with `defaultModelId: null` that demands an explicit choice.
    - **Mirror precedence.** The mirror is kept in lockstep with the registry by `worker/src/core/__tests__/aiModelCatalog.coherence.test.ts`, and `version` ranks only cache-vs-mirror — a served catalog always wins.
  - **Published-rate cost estimation** (`services/aiModelPricing.ts` — `estimateAiCostUsd` prices against the catalog descriptor's rates, returning `null` for an unknown or free model rather than a wrong charge).
  - **Context-window budgeting** (`services/aiContextBudget.ts` — pure `estimateContextUsage(counts, model?)` metered against a model's own window minus its output reservation, with the model-blind constants now just the catalog default's copy).
  - **Ports.** Provider-agnostic capability port (`AiService.ts`: `streamChat()`, `generateStructured()` — `AiChatRequest.model`/`AiGenerationRequest.model` carry an app-facing catalog id, never a provider); read-only model catalog port (`repositories/AiModelCatalogRepository.ts` — the app's best-known catalog, answered offline from cache/bundle).
    - **Local thread persistence** (`AiChatRepository.ts`) is local-only: sessions scoped to a material (`AiThread.materialId`), newest-session resolution, orphan recovery via `recoverInterruptedMessages`, and cascade deletion of a session's messages.
      - **Thread grounding is required and per-conversation.** `AiThread` carries no mode and **requires** `grounding` (`AiGroundingMode`: `'none' | 'whole'`), deliberately **unindexed**; absence is a property of the persistence row only, which `DexieAiChatRepository` normalizes away on read.
      - **The per-turn request fact.** `AiMessageRecord.metadata` optionally carries `grounding` — the material attached when that turn was sent — kept per turn because the thread's mode is mutable, so a `none → whole → none` conversation stays legible.
      - **Distinct states.** `'none'` means resolved-and-off while `undefined` means never resolved (failed turn or pre-field row), and the two are deliberately not collapsed.
  - **`AiTutorMode` survives only as the server-side prompt selector** on `AiChatRequest`.
- `preferences/` — Locally-stored user preferences: a **typed** port (`repositories/PreferencesRepository.ts`: `getAiGroundingDefault()` / `setAiGroundingDefault(mode)` plus `getAiSelectionThreadMode()` / `setAiSelectionThreadMode(mode)` for where selection actions reply, plus `getPreferredModelId()` / `setPreferredModelId(modelId)` for the next-request model choice) rather than a generic `get(key)`/`set(key, value)` pair, so stringly-typed storage and accidental cross-feature keys are unreachable from application code — the namespaced key is an adapter detail (`DexiePreferencesRepository`). Preferences are device-local: not in the sync entity model, and excluded from `.lcpack` import/export.
- `generator/` — AI content generation domain models and pure validators (`generator.types.ts`, `questionDraftValidation.ts`): structured question drafts, strict question payload validation across all 5 quiz types, and draft classification tags.
  - **There is no flashcard draft and no `validateFlashcardsDraftArray`.** A card is a projection of a typed question, and a `fill_in_blank` question projects one card per blank (see Card projection cardinality), so the retired `{front, back}` draft could only ever be persisted as a permanently-untyped `identification` row with a hardcoded difficulty. A card is generated by asking for `fill_in_blank` through `validateQuestionsDraftArray` like any other type.
  - **Tags.** `tags` are subject-matter keywords the model proposes for a draft — the review step offers tags a user can actually filter on. **No provenance marker is stamped**, because `ai-generated` / `sec:` markers cannot help anyone find or group a question.
  - **Generation requests carry `materialId` + an optional app-facing `model` and deliberately no document** — the source content is resolved by the use case through `AiGroundingResolver` (owner: `src/application/AGENTS.md`), so a caller cannot synthesize from a document the reader would not have offered.
  - **The array validator is salvage-based, not all-or-nothing:** it returns `DraftBatch<T>` (`{ drafts, rejected }`) and fails only when *nothing* survived, because one mistyped item (e.g. `true_false` typed as `_false`) must not discard its valid siblings — the review step is built to open on a partial batch and report the dropped count (owner: `src/features/ai/AGENTS.md`).
    - **Per-item validation never invents data.** A `multiple_choice`/`multiple_select` whose correct answer cannot be determined is **rejected, never defaulted to the first choice** (defaulting asserted a fact the model never supplied and marked a distractor correct).
    - **Payload-type salvage.** When the top-level `type` is unusable but `payload.type` names a real type, the payload's is adopted (the observed `_false` slip kept a correct `payload.type`, so the item is salvaged rather than lost).
  - **Cloze drafts are rejected, never repaired.** A `fill_in_blank` draft must carry at least one `___` marker in its `template` and exactly as many non-empty `blanks` as markers — the same rule the authoring path enforces in `quiz-management/drafts/quizDraftValidation` — so an already-resolved template or a marker/answer mismatch is rejected rather than repaired, because a mismatched blank would assert an answer the model never supplied and `questionToCards` would have no `___` marker to hide the card's own answer behind.
  - **The parity rule is enforced at every write boundary that could persist a generated draft**, not merely by convention, and it is the guarantee that a generated card's front always contains a valid `___`.
    - **Validator call sites.** The generator validates the model output, the review step re-validates per draft (a user can edit a draft between the two), and `BatchCreateQuestionsUseCase` — the single writer — re-runs **this same validator** as a gate before persisting. One rule, three call sites.
    - **One cloze rule.** A second cloze rule at the persistence boundary would be a rule that can drift. The boundary is salvage-based like the array validator (drop the offending item, keep valid siblings, never repair) and reports its refusals rather than shortening the batch silently.
- `importer/` — Content import domain: provider-agnostic ports (`ContentImporter`, `ImporterRegistry`, `ExtractionOptions`, `ImportAssetRepository`), domain types (`importer.types.ts`: `ExtractionResult`, `PageExtraction`, `ExtractionStats`, `ExtractionProgress`, `ImportMetadata`, `ImportCandidate`, `ImportSession`, `ImportError`, `ImportErrorCode`), and pure multi-pass markdown conversion pipeline (`markdownConverter/`: normalization, structure, page anchors, lists, tables, cleanup).
- `package/` — Portable study bundle domain: `StudyPackage` specification, pure schema and graph validator (`validateStudyPackage`), collision-free ID remapping engine (`remapStudyPackage`), package inspection engine (`inspectStudyPackage`), `StudyPackageSerializer` (pure JSON, Blob, and Base64 packaging serialization), and `StudyPackageImportService` application service port.
- `sync/` — Pure cloud synchronization domain: primitive types (`SyncEntityType`, `SyncOperation`, `SyncStatus`, `EntityVersion`, `SyncCursor`, `SessionCredentials`, `SyncMutation`, `SyncQueueItem`, `SyncState`, `ConflictDraft`, `ReconcileResult`, `SyncPushRequest`, `SyncPushResponse`, `SyncPullResponse`), strategy categorization (`SyncModel` + `getSyncModelForEntity`), monotonic cursor mathematics & validation (`isValidSyncCursor`, `assertCursorMonotonic`, `advanceSyncCursor`), composite sync identity (`createSyncStateKey`, `isValidSyncIdentity`), typed sync payloads (`DocumentSyncPayload`, `HighlightSyncPayload`, `DrawingSyncPayload`, `FlashcardReviewSyncPayload`, `QuizSessionSyncPayload`, `SyncPayloadMap`, `TypedSyncMutation`), optimistic concurrency & LWW resolution (`evaluateDocumentConcurrency`, `nextEntityVersion`, `compareLwwTimestamps`, `compareFlashcardReviews`), transport port contracts and DTOs (`SyncTransport`, `SyncPushRequest`, `SyncPushResponse`, `SyncPullResponse`), session credentials port (`SessionCredentialsProvider`), exponential backoff retry policies (`SyncRetryPolicy`, `calculateRetryDelay`), typed domain errors (`SyncError`, `SyncNetworkError`, `SyncHttpError`, `SyncProtocolError`, `SyncConflictError`, `OptimisticConcurrencyError`, `InvalidSyncPayloadError`, `InvalidSyncCursorError`, `OutboxTransactionError`), repository contracts (`SyncQueueRepository`, `SyncStateRepository`, `ConflictDraftRepository` with `resolveConflict`), and reconciliation port (`SyncReconciler`).
- `collections/` — Playlist-model grouping: `Collection` entity with `CreateCollectionInput`/`UpdateCollectionInput` DTOs (`models/Collection.ts`), `CollectionMaterial` M:N junction with per-collection ordering (`models/CollectionMaterial.ts`), and async repository contracts (`CollectionRepository` with `getAll`/`getById`/`create`/`update`/`delete`/`reorder`; `CollectionMaterialRepository` with `getByCollectionId`/`getByMaterialId`/`add`/`remove`/`reorder`/`removeByCollectionId`/`removeByMaterialId`).


## Local Contracts

- Zero React or UI dependencies. Domain modules import only from other domains or pure TypeScript libraries.
- Importable by any feature, application, or infrastructure layer.
- Domain logic must be testable without a browser environment.
- Analytics engines must never mutate their input arrays or domain objects.
- All timestamps in storage remain UTC ISO 8601 strings; date-key aggregations parse timestamps as instants and map to local calendar dates via `dateUtils.toLocalDateKey()`. Due comparisons use timestamp instants (`dueAt <= referenceDate`) before forecast grouping.
- Historical quiz attribution is derived strictly from immutable `questionSnapshots` on `QuizSession`, never from mutable question records.
- **`CardMaturityBreakdown` strictly partitions cards into mutually exclusive buckets (`new`, `learning`, `review`, `mastered`) satisfying `newCount + learningCount + reviewCount + masteredCount === totalCards` — and `totalCards` is the size of a set of projected card keys, never a question count.** `computeCardMaturity(reviews, cardKeys)` takes the **pool as a set**, built by `buildCardKeyPool(questions)` from the same `questionToCards` projection the study deck uses, so the analytics denominator and the deck cannot disagree about what a card is: every non-cloze question is 1:1 and a `fill_in_blank` question is 1 key per blank, so a three-blank cloze question beside two 1:1 questions is a pool of **five**. The archived exclusion lives inside `buildCardKeyPool` (only `status === 'archived'` is out of scope; drafts are in), and **every projected card counts, `multiple_choice` and `multiple_select` included** — the player renders their options as a genuine study interaction, so discounting them would understate the deck. Global scope is the union over every non-archived `Question` in the library; material scope is the same projection restricted to that material's questions.
- **A review counts only if its key is in the pool; anything else is an orphan, and an orphan is reported, never absorbed.** `orphanReviewCount` on the breakdown is a *diagnostic*: those rows are in no bucket, contribute nothing to `totalCards`, and therefore cannot break the partition invariant. **The `Math.max(totalCards, uniqueReviewMap.size)` repair is gone** — it silently widened the pool to cover reviews whose card no longer existed, which both relabelled a question count as a flashcard count and made an incorrect pool undetectable; the invariant is now checkable against the pool the caller actually derived, so a wrong pool is a bug rather than something the engine papers over. **An orphan is a CONDITION, not a cause, and the cause list is open:** the question was **deleted**, the question was **archived** (archiving is the app's soft delete, so the question still exists and only its keys left the pool — the cascade bullet below lists the *clearing* paths, and archive is deliberately not one of them), or a **cloze blank was retired**. Documentation and presentation must therefore never name a single one of them, which is why the Insights footnote reads "N schedule(s) sit(s) outside the active card pool". **This never throws in production**: orphaned rows already exist (see the deletion cascade below, and the pre-release no-migration decision for historical rows), and a thrown error would break the Insights screen over a diagnostic. Strictness is asserted in `engines/__tests__/retentionEngine.test.ts` instead, and the "N total flashcards" label carries the count as a footnote rather than folding it in.
- **Current-workload reporting is pool-scoped; historical reporting is not.** `computeReviewForecast(reviews, cardKeys, ...)` takes the same pool and drops a review whose card no longer exists — the forecast answers "what is coming", and a schedule for a card nothing projects is not upcoming work. `computeStudyOverview(sessions, reviews, cardKeys, ...)` splits on the same line: `cardsWithReviewHistory` counts **current** cards (pool keys with `reviewCount > 0`) because it renders directly above the maturity bar and must not contradict it, while `totalCardReviews`, the last-activity stamps, and the streak they feed stay on **full** review history because a review of a since-archived or since-deleted card still happened. The pool is a **required** parameter, not an option, so the two figures cannot be measured against different denominators; `DexieAnalyticsRepository` builds it once and hands the same set to all three engines. There is no separate all-time distinct-card count — an unqualified one would silently include archived and removed cards. `buildActivityCalendar(sessions, reviews, ...)` deliberately does not scope: it is historical, and scoping it to the pool would silently rewrite study history (pinned by a paired forecast/calendar case in `engines/__tests__/retentionEngine.test.ts`).
- Global quiz accuracy is question-weighted (`totalCorrectAnswers / totalAnsweredQuestions * 100`).
- Topic mastery counts total answer attempts (`attemptCount`), not unique questions. Status includes `unattempted`, `needs_practice`, `proficient`, `mastered` (mastered requires $\ge 85\%$ weighted score AND $\ge 3$ attempts).
- `LibraryRepository` is the async contract (interface) that infrastructure implementations (e.g., `DexieLibraryRepository`) must satisfy. It deliberately declares **no delete**: `LibraryImportService.removeMaterial` is the single removal contract, so no caller can delete a material row without clearing its questions, quizzes, document content, collection membership, stored assets, **and its `flashcardReviews` schedules** — removing a material removes its questions, and a question's cards are the only thing that projects its review keys, so a material removal that skipped them would manufacture a block of permanent orphans. Since a material's dependencies can be acquired after creation, a cheaper row-only delete is never safe.
- `AssetRepository` is the async read-only contract for locally stored binary assets: `get(assetId)` resolves one asset by the identity a document reference carries, `getByMaterialId(materialId)` returns every asset grouped under a material (implemented by `DexieAssetRepository`). Read-only is a **contract** property, not a naming one: ports keep the repo-wide `*Repository` suffix (adapters `Dexie*Repository`) and the two-method surface is what keeps this one write-free. **`assetId` is identity — exactly one blob per id; `materialId` is only the grouping index and never identifies an individual asset.** `AssetRepository` must stay minimal (no `.lcpack`, remapping, `pkg_asset_*`, or import-session concepts) and write-free: asset writes belong to the persistence paths that own them, so the reader never becomes a second persistence boundary. The importer's `ImportAssetRepository` remains the single-asset **write-only** contract (`put`; one original PDF/image per material, written as `assetId = materialId`) — asset deletion belongs to the removal transaction that owns it (`DexieLibraryImportService.removeMaterial`), not to a port.
- `DocumentRepository` is the async contract for resolving `StudyMaterial` → `Document` (implemented by `HybridDocumentRepository` in `src/infrastructure/storage/repositories/`).
- `AnnotationRepository` is the async contract for highlight/drawing persistence keyed by `documentId` (implemented by `DexieAnnotationRepository`).
- `QuestionRepository`, `QuizRepository`, `QuizSessionRepository`, `FlashcardReviewRepository` are async contracts for persistence (implemented by Dexie repositories in `src/infrastructure/database/repositories/`). `QuestionRepository.deleteQuestion` is a **cascade, not a row delete**: it owns clearing the deleted question's card review keys through `FlashcardReviewRepository.deleteByKeys` (see the review-clearing contract below), so no caller can delete a question and leave a stranded SM-2 schedule behind.
- `SyncQueueRepository`, `SyncStateRepository`, `ConflictDraftRepository` are async contracts for persistence of cloud sync mutations, checkpoint cursors, and branched conflict drafts.
- `CollectionRepository`, `CollectionMaterialRepository` are async contracts for playlist-model collection persistence (implemented by Dexie repositories in `src/infrastructure/database/repositories/`).
- `SyncTransport` is the domain port contract for HTTP sync transport pushing mutations and pulling change deltas.
- All sync payloads, version numbers, and cursors enforce strict pure-domain invariants: cursors are monotonically increasing non-negative integers; documents use Model C optimistic concurrency with conflict draft branching; highlights, drawings, and flashcards follow Model A deterministic LWW semantics; quiz sessions follow Model B append-only semantics.
- **A `flashcardReview` delete is a tombstone, and the tombstone is not optional.** `FlashcardReviewRepository.deleteByKeys` is the only way review state is cleared, and its adapter writes a `DELETE` `syncQueue` item in the same `db.transaction('rw', [flashcardReviews, syncQueue])` as the row delete. `DELETE` is supported for this entity end to end — `SyncOperation` admits it, the Worker's LWW branch stamps `user_entities.deleted_at` and records a `sync_changes` `DELETE` (pinned by `worker/src/__tests__/syncProtocol.test.ts`), and the pull reconciler drops the local row. A local-only delete would be undone by the next pull, resurrecting the schedule with stale SM-2 state, so an outbox write is part of the delete contract rather than an optimisation. The tombstone's `clientTimestamp` is the moment of deletion (`save` prefers the entity's own `lastReviewedAt` and falls back to `now`; a deletion has no entity payload, so it takes that fallback), which keeps it strictly newer than the UPSERT that created the row — the Worker only applies a mutation whose timestamp is `>=` the stored `updated_at`.
- **A card stops existing when its question stops projecting it, so every such path clears that card's review keys through `deleteByKeys`.** Two paths, and both are cascades rather than row deletes: `QuestionRepository.deleteQuestion` clears the deleted question's `q:<questionId>` key and every `q:<questionId>#<blankIndex>` key it owns, and `LibraryImportService.removeMaterial` clears every review row of the material it deletes. The keys are read from **storage by key prefix / `materialId` index, never re-projected from the current question row**, so a key left by an *earlier* card shape is cleared too — a question that was once a 3-blank cloze and is now 1:1 still has `#0..2` rows, and re-projecting would only find `q:<id>`. The prefix is always `q:<id>#` and never the bare `q:<id>`, because a `startsWith` on the bare key would also match a different question whose id merely extends this one. **This is forward-looking only, and does not contradict the pre-release no-migration decision below:** that decision covers *historical* rows accumulated before the per-blank re-key; it does not license ordinary new deletions to manufacture orphans that nothing can ever retire. **Archiving is deliberately a third way a card leaves the pool, and deliberately not a clearing path:** it is reversible, so clearing a card's reviews on archive would destroy study history the moment the author un-archives the question. Archive only removes those keys from `buildCardKeyPool`, and the stranded rows it leaves are exactly the reported orphan diagnostic.

- `AssessmentService` is a pure domain service with zero persistence dependencies — validates, grades, and computes `QuizResult`/`QuizScore` via strategy dispatch.
- **One strategy keeps a guard after the read tier was removed, and it is a different kind of rule.** `FillBlankStrategy.validate` and `.grade` both carry `blanks.length > 0`, and it is **not** a tolerance for malformed content: every ingress to `db.questions` validates, so a cloze with an empty answer set is a real question the Bank is allowed to hold. What the clause defends is narrower and permanent — substituting an empty answer set for any reason must never become a **vacuous match**, because with zero answers `every` over the submission is trivially true and an EMPTY submission would otherwise be graded correct, taking the question's points. `IdentificationStrategy` keeps only the ordinary `?? []`: `acceptedAlternatives` is optional, so absence is the case `?? []` actually covers, and the alternatives are decoration — `correctAnswer` is the basis grading rests on either way. Neither strategy reads a non-array any more. The other three strategies are unchanged, and no broad "never throws" claim is made for grading — each further payload field would need its own reading and its own test.
- **Card projection cardinality (`questionToCards`): a question projects to 1..N cards, never 0.** Every non-cloze type is 1:1.
  - **Cloze cardinality is 1:N.** A `fill_in_blank` question yields one `recall` card per blank, each with its own `q:${questionId}#${index}` key and therefore its own SM-2 schedule (the Anki cloze model).
    - **Front.** The resolved template with the *target* blank left as `___` and every other blank filled with its answer (retrieval context).
    - **Back.** That one answer only.
  - **Fallbacks are single cards, never zero.** A row with no answers, or whose `___` marker count disagrees with its `blanks` count, keeps the legacy whole-question card.
    - **Why not drop it.** Dropping it would silently remove the question from the deck.
    - **Why not guess.** Guessing a marker/answer pairing would print an answer on the card's own front.
    - **Both are reachable states of a real authoring surface, not tolerated defects:** an answer set the author has not written yet is a question the Bank is allowed to hold, and a marker/answer mismatch means a row stored before the write boundaries validated.
  - **Validated ingress.** The projection reads `blanks` and `acceptedAlternatives` directly — **every ingress to `db.questions` validates, so neither field is ever a non-array here** (`acceptedAlternatives` is optional, so `?? []` covers exactly the ordinary absence).
  - **Identity is `key`, not `source.questionId`.** Consumers that count a deck must count projected cards, never questions.
  - **The re-key, and the pre-release decision that follows.** Adding the `#${index}` key re-keys every `fill_in_blank` card, so any review state stored under the old whole-question key stops resolving. The project is pre-release, so no user has accumulated state to lose: there is no migration and no orphan-cleanup debt, and local rows from before the re-key are disposable through the existing database reload path.
    - **If real usage ever arrives.** A lookup fallback (`q:${questionId}#0`, else `q:${questionId}`) restores single-blank history exactly and mis-attributes multi-blank questions to blank 0.
    - **Scope: HISTORICAL rows only.** It removes the need to sweep rows the old key scheme left behind; it does not license an ordinary forward-looking delete to strand fresh ones, so the deletion cascade contract above is still binding.
- **The resolved cloze front is one function, and it is the reset policy's unit of comparison (`clozeCardFront.ts`).** `resolveClozeCardFront(prompt, template)` returns the text a `fill_in_blank` card shows before expansion: a `template` carrying no cloze text — **empty or whitespace-only, which is a real state a question is in before its author writes the template** — reduces the front to the `prompt`, the only text such a row has; an empty prompt, or one containing "fill in the blank", contributes nothing and the front is the bare `template`; a prompt that is neither the template itself nor blank-bearing is real prose and is prefixed above the template; a prompt already carrying `___` **is** the cloze source and wins outright, so the template is not read at all. `questionToCards` renders it and the invalidation predicate compares it — never a second copy, because a drift between the two would mean the policy silently stops matching what the learner is shown. **`template` is typed `string`.** It was once `unknown` and normalised here so both callers inherited one reading of a value the static type claimed could not exist; that was only necessary while the package read tier admitted a row carrying no usable `template`, and **no ingress produces one now**, so the parameter is honest as written. The empty-template rule survives because it is about a legitimate authoring state, not about malformed data. `prompt` is **not** widened or normalised, because the validator refuses a non-string prompt, so it is a real defect and must still throw. Changing the front a card displays therefore means changing this function, and the rendered fronts are pinned byte-identically per branch in `engines/__tests__/clozeCardFront.test.ts`, including the empty-template cases driven through the real `questionToCards`.
- **Cloze schedule invalidation (`clozeReviewReset.ts`): a per-blank schedule's identity is the fact it was earned on, so it dies with that fact.** `affectedClozeBlankIndices(before, after)` is the single owner of which per-blank keys a question edit invalidates; the key format itself is owned by Card projection cardinality.
  - **It compares the resolved card front** (`resolveClozeCardFront`, the same function the projection renders) rather than `template` and `prompt` separately — invalidation must follow the content the learner is actually tested on.
    - **A reworded generic prompt resolves to the same front and invalidates nothing**, while a real non-generic prompt *is* part of the front and invalidates.
    - **There is no second template check.** The resolved front **subsumes** a direct `template` comparison: a template edit changes the front wherever the template is rendered, and where the prompt holds the markers the template is not rendered, so no schedule can have been earned on it.
  - **An empty `blanks` is handled by arithmetic, not by a guard:** such a row holds no per-blank schedule, so every index derived from it is correctly empty.
  - **A changed `blanks.length` or a reorder resets ALL of the question's blank keys**, because a reorder makes key #1 ask what #2 used to ask, so per-index comparison alone would leave a history attached to the wrong fact. A single answer rewritten **in place** resets only that index.
  - **Everything the front and the blanks do not render is ignored:** `version`, `status`, `points`, `tags`, `explanation`, `difficulty`, `materialId`, quiz membership and `order`.
  - **The rule is asymmetric about cloze-ness, because the keys are:** a cloze question converted to another type retires **all** of its blank indices (nothing projects a per-blank key any more, so they would sit in `flashcardReviews` forever as orphans), while a question that only just became cloze retires nothing (its per-blank keys are new and can hold no history; the question's single `q:<id>` key belongs to a card shape that no longer exists and is a separate concern).
  - **The comparison is content-based and deliberately NOT version-based** — `version` increments on *every* update, publish and archive included, so keying off it would wipe a question's study history each time it was published.
  - **Comparison is trimmed + case-folded**, matching `FillBlankStrategy`'s `v.trim().toLowerCase() === blank.trim().toLowerCase()`: the grader already calls `"Mitochondria"` and `"mitochondria "` the same answer, so a cosmetic edit must not reset a schedule the grader considers identical.
  - **The predicate is pure**; the capture/write/delete **bracket** around it, and that bracket's known non-self-healing retry limitation, are owned by `src/application/AGENTS.md`.
- Tag casing policy (case-preserving display): stored tags keep the FIRST casing seen (`iOS` displays as `iOS`); `tagKey` (lowercase) is the derived canonical key for dedup/comparison and is never persisted. `normalizeTags` — a pure string helper in `shared/utils/tags.ts`, not a domain module — is the write-boundary normalization every tag write must pass through (repositories, editor service, migration) — question tags AND `StudyMaterial.tags` alike. Tags describe what content is about, live directly on the entity (no foreign keys), and are portable across `.lcpack` packages and cloud shares.
- `virtualQuiz.ts` generates derived, in-memory Virtual Quiz domain objects (`virtual:quizzes:...`) without mutating database state.

## Work Guidance

- **Uniform Domain Organization (ADR-013)**: Domain code is strictly organized into authorized responsibility subdirectories (`models/`, `repositories/`, `services/`, `engines/`, `context/`, `strategies/`, `reconcilers/`, `validation/`, `policies/`, `factories/`, `errors/`, `utils/`).

- **Primary Unit Test Discoverability & Colocation (ADR-012)**: Every testable domain behavior unit possesses a dedicated primary unit-test file named after the unit (`<UnitName>.ts` $\leftrightarrow$ `__tests__/<UnitName>.test.ts`), colocated within a `__tests__/` directory inside the specific responsibility folder where the tested unit resides.
- Domain tests must be 100% pure, deterministic unit tests with zero mocks (`vi.fn()`) — instantiate real classes and test observable input/output contracts.
- Spaced repetition, due dates, and timestamp comparisons must always supply a fixed reference instant (e.g. `new Date('2026-09-01T12:00:00.000Z')`), never non-deterministic `new Date()`.
